# Промт исполнителю · ДИАГНОСТИКА ЗАВИСАНИЙ — чтобы каждый полевой эпизод был понятен и воспроизводим без вопросов к игроку

Выдан 2026-11-14. Для автономной работы на несколько дней. Исполнитель — архитектор (Fable 5.2).

**Миссия.** Зависания — блокер продакшена. Новая архитектура консоли (ядро флоу, `docs/claude/console/architecture-v2/`)
должна была сделать их редкими. Подтвердить это или опровергнуть могут только данные с поля и с бокса, а чинить
остаток — только по уликам. Подсистема диагностики (`docs/claude/diagnostics.md`) уже доставляет события в Sentry:
транспорт, приватность, согласие, очередь, бюджеты, эпизоды зависаний, отчёт игрока. **Твоя задача — сделать так,
чтобы агент, который будет разбирать эти события, находил ВСЁ нужное для причины и исправления одной-двумя командами,
не копаясь в мусоре, и чтобы владелец получил честный ответ на вопрос «зависаний стало меньше?».**

Потребитель этой работы — агент-разработчик, который чинит зависания. Ниже его требования, написанные им самим. Это
требования, не дизайн: как их выполнить, решаешь ты. Ищи самые сильные решения — в нашем коде, в возможностях Sentry
(fingerprint rules, grouping, tags, contexts, attachments, release health / sessions, alerts, issue states, API), в
устройстве ядра флоу. Если найдёшь подход сильнее описанных здесь ориентиров — делай его и запиши почему.

## 0. Режим работы

- **Автономно, от исследования до приёмки.** Решения принимаешь сам; каждое существенное решение — строка в журнале
  решений `docs/claude/diagnostics.md` § 10 (что выбрано, варианты, почему).
- **Непреложно:** законы проекта (`CLAUDE.md`, `.claude/rules/*.md`, особенно `.claude/rules/diagnostics.md` и
  `.claude/rules/console-flow.md`), раздел 3 «Ограничения» и раздел 4 «Приёмка».
- **Вехами.** Каждая веха оставляет продукт рабочим: коммит → пуш (только свои пути; `main` общий с другими сессиями).
  Бокс обновляется с `origin/main` через релиз, владелец играет между вехами.
- **e2e:** точечно, на боксе (`npm run e2e:remote -- <task> <spec…>` по `.claude/rules/tests.md`), никаких полных
  прогонов — полный прогон делает владелец на CI в конце. Логику — дешёвыми юнит-спеками.
- **Спрашивать владельца только** о том, что стоит денег или меняет то, что видит игрок.

## 1. Что есть сейчас и где больно (факты, проверены 2026-11-14)

Прочитай целиком: `docs/claude/diagnostics.md`, `.claude/skills/diagnose-report/SKILL.md`,
`docs/claude/console/architecture-v2/KERNEL.md`, `PLAN.md` §0 и §6 (какие сетки ещё стоят и «уходят по полевым
данным»), `docs/claude/console/liveness-arbiter.md`, `docs/claude/console/wait-graph.md`.

Единственное событие зависания, которое пока пришло (проба, `TERRAFORMING-MARS-39`, `npm run diag -- issue TERRAFORMING-MARS-39`):

```
[liveness] the screen stood still (unserved, asked card) — cured after 13s
screen: prompt card#12 · accepting false · block reveal · frames hand:committed · in_flight [] · quiet 12s
episode: healed 13s · steps: «rung 0: presentation stories degraded»
breadcrumbs: 2 · attachments: none
```

Из этого видно, ЧТО экран стоял, но не видно, ПОЧЕМУ. Конкретные дыры:

1. **Нет причины в событии.** `DiagScreen` — heartbeat полевого журнала, урезанный: выброшены `graph` (дайджест графа
   ожиданий), `flow` (дайджест дерева флоу — главное, что даёт новая архитектура) и `start`. Полная строка арбитра
   (`claim: … (zone, beat, arrival, task …)`, `holds: …`, `stranded: …`, `last in flight: …`) в событие не попадает —
   только «unserved, asked card». Нет дерева областей / таблицы ожиданий в момент зависания (`window.__conFlow()`,
   `dumpFlowTree()`, `waitTable()`), нет последних переходов машин (`flowTraceLines()`).
2. **Группировка грубая.** Отпечаток эпизода — `['stall','liveness', reason, asked, healed|unhealed]`: все «unserved,
   asked card» склеятся в одну проблему, будь то claim, переживший хост, блок раскрытия или зависший холд. Классы
   нельзя посчитать и нельзя закрыть по одному. Обратная беда у прочих строк: отпечаток —
   `[kind, family, normalizeMessage(title)]`, и одна причина в разных формулировках может разъехаться.
3. **Шум съедает бюджет и квоту.** Как отдельное событие уходит каждая строка `stall`-семейств: `[wait-graph] ceiling …`,
   `[flow] bound …`, `[animation-hold] … force-released`. Многие из них — ПЛАНОВЫЕ ожидания, дошедшие до своего потолка
   (в полевых логах `ceiling remote-placement:watchable-board` 5–8 раз за партию: чужой тайл ждёт открытой доски,
   пока игрок в workspace, — это не дефект). Бюджет — 8 событий на СЕМЕЙСТВО за запуск: плановые потолки могут
   исчерпать его раньше настоящего `dead-end` / `cycle` той же сессии, и тот не уйдёт. Квота бесплатного плана —
   5 000 событий и 1 ГБ вложений в месяц.
4. **Нативная остановка рендерера приходит без улики.** `[renderer-hang]` уходит строкой, а трейс Chromium
   (`electron/hangTrace.ts`, `hang_trace.json`) — единственное, что объясняет остановку вне JS, — прикладывается только к
   явному отчёту игрока. Строки `[long-frame]` — `perf`, то есть только хлебные крошки следующего события.
5. **Нечем воспроизвести.** Самый быстрый путь к исправлению у нас был: сохранение партии → фикстура → e2e (так закрыт
   Hi-Tech Lab, `tests/e2e/console-hi-tech-lab.spec.ts`). Сохранение едет только с явным отчётом. При зависании
   геймпад мёртв — игрок отчёт не нажмёт: автоматическое событие должно быть самодостаточным.
6. **Нет ответа на вопрос владельца «стало меньше?».** Нет знаменателя (сессии / часы игры), нет сравнения релизов,
   нет счёта срабатываний каждой сетки (а PLAN §6 снимает сетки именно «по полевым данным»).
7. **Сетки, которые сработали молча, не видны как дефекты.** `[wait-graph] cure …`, `[flow] cycle refused …`,
   освобождённый claim, принудительный демонтаж — игрок мог ничего не заметить, но каждая такая строка — дефект выше
   по течению (так их и описывает KERNEL §3). Сейчас они либо тонут в шуме, либо не связаны с эпизодом, внутри которого
   случились.

Корпус реальных полевых зависаний для проектирования классов и ключей (экспорты консоли владельца, на этом ноутбуке):

## 2. Требования потребителя (что должно стать возможным)

### R1. Причина — внутри события
По одному событию зависания (или срабатывания сетки) агент называет причину, не открывая код и не прося отчёт:
- что спросил сервер и что должно было его обслуживать; кто держал (блок допуска, холд, claim, такт, ожидание) и сколько;
- дерево флоу и таблица стоящих ожиданий **в момент начала** эпизода (кто кого ждёт, их возраст и пределы), и что
  изменилось к моменту лечения;
- полные строки арбитра эпизода и какая ступень / дверь / сетка его вылечила;
- последние переходы машин и открытия/концы областей перед эпизодом;
- для ошибки внутри флоу — какой области/машины она была (`failed` у scope) и стек с исходниками.
Всё ограничено по размеру, вычищено той же приватностью, снимается в момент события (страница при логическом зависании
жива) и не стоит кадра.

### R2. Группировка — умная, а не отменённая
Группировка остаётся главным инструментом: меньше мусора, легче искать, легче по лимитам. Она должна стать УМНОЙ:
- **одна проблема в Sentry = один класс причины**, устойчивый между сессиями, игроками, релизами и мелкими правками текста
  строк; разные причины не склеиваются, одна причина не дробится;
- **внутри проблемы** каждое событие несёт измерения, по которым можно резать без захода в события: источник (карта /
  флоу / workspace / секция), тип вопроса, держатель, вылечившая сетка, исход (вылечено / нет / перезагрузка),
  длительность, релиз, окружение (бокс / игроки), профиль экрана;
- **связность**: всё, что произошло внутри одного эпизода (сетки, ошибки, пределы), связано с эпизодом и находится от
  него одним шагом;
- **тот же ключ класса — в e2e-харвесте**: красный спек на CI / в обезьяне и полевая проблема с одной причиной имеют один
  и тот же ключ, чтобы полевой случай находил воспроизводящий спек, а спек — свои полевые случаи;
- новая строка-тег не может молча попасть не в тот класс (продолжи гард `diagnosticsClassification.spec`).
Как строить ключ — решаешь ты (клиентский отпечаток, правила группировки Sentry, их сочетание). Обоснуй выбор.

### R3. Сигнал отдельно от шума
- Дефект (не вылеченное зависание, вылеченное зависание, сработавшая сетка, отказанный цикл, предел, оборвавший
  РЕШЕНИЕ, исключение во флоу) — событие.
- Плановое ожидание, дошедшее до своего потолка, медленный, но здоровый такт, перф — не отдельное событие, а агрегат или
  хлебная крошка, по которому всё равно можно посчитать частоту.
- Бюджеты такие, что шум никогда не вытесняет дефект (подумай о бюджете по ключу дефекта, а не по семейству), и
  месячная квота не кончается на первой же неделе с несколькими игроками.

### R4. Нативные остановки — с уликой
Событие `[renderer-hang]` несёт трейс Chromium: на боксе всегда, у игроков — с согласия и в пределах бюджета вложений.
Оно же называет последний экран перед тишиной. Длинные кадры (`[long-frame]`) агрегируются за сессию так, чтобы было
видно, на каком экране и в какой фазе (стиль / раскладка / отрисовка / скрипт) теряется время.

### R5. Воспроизводимость
- Не вылеченное зависание на боксе (режим host) несёт сохранение партии в момент начала эпизода (или надёжную ссылку,
  по которой `npm run diag` его достанет — сохранения истории партии на боксе есть).
- Есть путь от проблемы к локальному воспроизведению: из события — фикстура для e2e (как `hi-tech-lab`), минимум
  ручного труда. Как — решаешь ты.

### R6. Ответ на «стало меньше?»
Одна команда показывает по релизам: зависаний на час игры (и на сессию), доля вылеченных / не вылеченных / ушедших в
перезагрузку, распределение времени до лечения, топ классов и их тренд, счёт срабатываний КАЖДОЙ сетки (доказательство
для снятия сеток по PLAN §6). Нужен знаменатель — сессии и время игры; как его получить (release health Sentry, свой
агрегат, что-то ещё) — решаешь ты, с учётом квоты.

### R7. Инструменты разбора (`npm run diag`, `scripts/diag.mjs`)
- список классов за период / релиз / окружение со счётом и трендом;
- открыть класс: последние N случаев со всеми уликами, разложенные в папку в порядке чтения (как сейчас `report` →
  `SUMMARY.md`);
- регресс: класс, закрытый в релизе X, снова пришёл в более новом — видно сразу (и оповещение, если это дёшево);
- закрыть класс «исправлено в релизе» из командной строки;
- от владельца области флоу / метки строки — к файлу исходника (как кадры стека уже читаются через symbols).

### R8. Навык разбора
Обнови `.claude/skills/diagnose-report/SKILL.md` (или заведи соседний навык под зависания): порядок чтения улик
зависания, как найти класс, воспроизвести, проверить, что исправление закрыло класс в следующем релизе.

## 3. Ограничения (непреложно)

- **Законы диагностики** (`.claude/rules/diagnostics.md`): одна дорога сигнала на рантайм, страница не запускает SDK и
  ничего не шлёт сама, хаб — единственный отправитель, вычистка до отправки (id → отпечаток, имена, пути, адреса),
  согласие игрока у хаба, ничего из сборки без назначения и из тестового прогона, **зависание никогда не показывается
  игроку**, ключ клиента ни в одном файле, новый тег — новая строка классификации.
- **Законы ядра флоу** (`.claude/rules/console-flow.md`, `REVIEW.md`): снимок дерева и таблицы ожиданий — только
  чтение; ничего, что ждёт, вне области; никакой новой сетки, ступени, двери или флага ради диагностики.
- **Цена:** диагностика не имеет права стоить кадра, который описывает (D30). Ничего на кадр и на тик сверх нынешнего;
  тяжёлое (снимок дерева, трейс) — только в момент события и ограничено по размеру. Замерь до и после, как в § 9.1.
- **Квота и лимиты:** бесплатный план (5 000 событий, 1 ГБ вложений в месяц); правило D33 — лимит не называть «нет сети».
- **Игрок:** ни одного нового элемента на экране игры; изменения поверхности «Диагностика» — по её законам (одна
  карточка, которая не двигается; e2e `console-diagnostics.spec.ts` расширяется в том же диффе).
- **Приватность новых полей:** дерево флоу и строки сеток могут нести id партии/места и имена — вычищаются по
  конструкции, без исключений.

## 4. Приёмка

Положительные контроли на боксе, в окружении с настоящей отправкой (как `scripts/diag-probe.mjs` / `TM_DIAG_PROBE`,
§ 9.2 документа диагностики). Контрольные швы зависаний возьми существующие (поищи `waitGraphControl`, `__conStillHold`,
`__conStrandQuestion`, `__conOrphanClaim` — после архитектуры v2 часть могла уйти) или построй свои:

1. Два зависания с РАЗНЫМИ причинами → две проблемы в Sentry; одно и то же зависание в трёх сессиях → одна проблема со
   счётом 3. По каждому событию агент называет держателя и вылечившую сетку командой `npm run diag -- …`, не открывая
   код.
2. Плановое ожидание, дошедшее до потолка, не создаёт проблемы; его частота видна в агрегате. Сотня таких строк в одной
   сессии не мешает уйти настоящему `dead-end` той же сессии (юнит-спека бюджетов).
3. Не вылеченное зависание с перезагрузкой страницы приходит как «ушло в перезагрузку» с уликами момента начала.
4. Контрольная нативная остановка → событие с трейсом Chromium на боксе.
5. Не вылеченное зависание на боксе → сохранение партии доступно через `npm run diag`, и из него получается
   работающая e2e-фикстура (докажи на одном случае).
6. Ключ класса из e2e-харвеста совпадает с ключом полевой проблемы той же причины (докажи на контроле).
7. Команда R6 печатает показатели по релизам (на пробах — хотя бы по двум релизам или окружениям).
8. Цена: тайминговый набор и размеры бандлов до/после — без регресса (как в § 9.1).
9. Гарды зелёные: `diagnosticsClassification.spec`, `diagnosticsHub.spec`, `diagnosticsCore.spec`,
   `diagnosticsHubConform.spec`, `fieldRecorder.spec`, `diagnosticsClient.spec`, `kernelCoverage.spec`,
   `architectureDebt.spec`; `npm run lint`, `npm run build:test`; точечно на боксе — `console-diagnostics`,
   `console-system-menu`, контроли зависаний.
10. Документы: `docs/claude/diagnostics.md` (новые разделы + журнал решений), навык разбора, `.claude/rules/diagnostics.md`
    — если появились новые законы; `MEMORY`-уровень не трогай.

В конце — короткий отчёт владельцу (по-русски): что теперь приходит по одному зависанию (пример реального события
контроля), как устроена группировка, как читать показатель «стало меньше», что осталось открытым.
