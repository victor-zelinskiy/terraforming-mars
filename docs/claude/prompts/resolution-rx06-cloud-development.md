### Правило, как его надо понимать

1. **Сколько:** `N = метки Венеры + метки Юпитера + влияние` — у каждого игрока своё. Метки считаются

2. **Куда:** на СВОИ карты, способные нести флоатеры (`getResourceCards(CardResource.FLOATER)`,

   красной рамки, которой отмечается чужая цель. Проверь это прочтение по соседним картам Venus Next в
   движке, не на слово.
3. **Как:** N единиц распределяются свободно: от 0 до N на карту, **сумма ровно N**. Всё на одну — тоже
   законно.
4. **Кладёт движок**, через `addResourceTo`, чтобы сработали штатные триггеры. Прогресс задания
   председателя от этого не растёт (Q5; `QuestTracker` это уже обеспечивает по источнику на стеке —
   закрепи спеком, не правкой).
5. **Пропуск называет себя с величиной** (инвариант 4): N = 0 — своя причина; N > 0, но ни одна карта не
   держит флоатеры — «N флоатеров: ни одна ваша карта не держит флоатеры» по образцу RX01 («No card can

## 2. Что в этой карте нового — и почему это не частный случай

### 2.1 Распределение по картам — новая форма семейства

Сегодня `cardResource` в таблице адресов знает одну цель: RX01 кладёт всё на одну выбранную карту
(`AddResourcesToCard`, `autoSelect: false`). Распределения по нескольким картам в семействе нет.

В движке есть `AddResourcesToCards` (им пользуются Cyanobacteria, Communication Boom, Philares), но
взять его как есть нельзя:

- **при одной подходящей карте он кладёт всё сам**, не показывая выбора. Это прямое нарушение
  инварианта 3 («никакого автовыбора, никакой скрытой цели»), ровно поэтому RX01 и ставит
  `autoSelect: false`;
- на проводе это `AndOptions` из голых `SelectAmount` **без структурного маркера**: консоль маршрутизирует
  его как `composite` и рисует безликую колонку чисел. Задача `distribute` в роутере обслуживает только
  стандартные ресурсы (`SelectResources`) и потерю производства — карт с ресурсами она не знает.

Что требуется — и это главная инженерная часть итерации:

- **Серверная сторона, две формы одного шага.** Распределять есть что, только если `N ≥ 2` И подходящих
  карт `≥ 2`. Во всех остальных случаях (`N = 1`, или карта одна — тогда на неё идут все N) шаг задаёт
  **обычный выбор карты**: `AddResourcesToCard` с `autoSelect: false`, ровно путь RX01, со штатным
  маркером `resourceGainPrompt`. Иначе — промпт распределения со структурным маркером (распознаётся по
  маркеру, никогда по заголовку — инвариант 1). В обеих формах шаг проверяет сумму, применяет через
  `addResourceTo` и вызывает `ctx.report` **ровно один раз**. Шаг возобновляем: перезагрузка посреди
  выбора пересобирает тот же промпт (контракт `EnactStep`: либо мутирует, либо спрашивает, никогда оба).
- **ПО на рельсе — только серверные, для каждого k.** Сегодняшний `ResourceGainPromptMeta.vpBox` несёт
  дельту ПО по карте для ОДНОГО фиксированного количества. При распределении на карту может лечь любое
  k от 1 до N, а ПО за флоатеры часто ступенчатые («1 ПО за 2 флоатера»), так что из дельты для одного
  количества дельту для k не вывести — а выводить правила на клиенте запрещено (инвариант 7). Промпт
  распределения несёт по каждой карте чтение ПО для каждого k = 1…N, посчитанное той же машиной
  `VictoryPointsDelta`, что и `vpBox`. Таблица маленькая (N редко больше десятка, карт — единицы).
- **Модель исхода:** вид `cardResource` расширяется списком «карта → сколько», а не заводится новый
  вид. Каждый потребитель исхода — чтение стадии НАГРАДА, выплаты в итогах, журнал, нотификации —
  читает список; одна цель — частный случай списка из одного элемента.
- **Одна реализация, а не две.** Если распределение резолюции и `AddResourcesToCards` расходятся в
  двух параллельных механизмах, это технический долг с первого дня. Реши осознанно: либо общий
  механизм, которым могут пользоваться и три карты проектов (перевод их — бонус, не обязанность, но без
  регрессий), либо обоснуй разделение в журнале. Молчаливых двойников быть не должно.
- **Счётный член по двум меткам.** Если `ResolutionCountTerm` сегодня берёт одну метку — расширь его до
  суммы меток как член семейства (объявление в данных, чтение прогноза с разбивкой по каждой метке), а
  не особой веткой для одной карты. Прогноз голосования, чтение НАГРАДЫ и «Полигон» получают это из
  декларации сами.

### 2.2 Встроенный шаг «распределить» — здесь максимум усилий на подачу

Это новый выбор, и он должен выглядеть так, будто был в продукте всегда. **Модель взаимодействия
решена владельцем** (ниже, «Одно шасси»); визуальное исполнение, композиция и моушен — твои. Ниже —
контракт, который нельзя нарушить.

**Одно шасси, два режима.** Основа — существующий выбор карты из сетки (`ConsoleTaskHost`, режим
target): сетка настоящих лиц карт и статус-строка под сеткой, которая уже показывает для карты в фокусе
`было → станет` по ресурсу и **ПО** (серверный `resourceGainPrompt`, `con-cards__verdict--impact`).
- **Выбор одной карты** (`N = 1` или карта одна) — это он и есть, без изменений: RX01 уже так работает.
- **Распределение** (`N ≥ 2` и карт `≥ 2`) — **тот же компонент в режиме раскладки**, а не соседний
  компонент «похожего вида». Та же сетка, те же лица, та же статус-строка; добавляется только счётчик
  на каждой карте и остаток. Похожесть обеспечивается конструкцией, а не старанием — два компонента со
  временем расходятся.
- **Всё — предвыбор.** Игрок раскладывает, как хочет, меняет решение сколько угодно, и только A
  подтверждает. До A на сервер не уходит ничего.

**Место в сцене.** Шаг берёт ТЕЛО средней зоны через уже существующий слот
`[data-embed-slot="parliament-stage"]`, как встроенный добор RX05. **Резолюция остаётся слева
героем**, лента не меняет высоту, смена тела идёт утверждённой грамматикой контракта зон v5 (ряд партий
уходит вниз, шаг раскрывается из-под ленты, карта-носитель отдаёт импульс как причину; возврат
симметричен) и только после посадки последнего объекта такта.

**Крошка.** Шаг не титулует себя: имя стадии он передаёт наверх (`setWorkspaceOutcomePhase`), хвост
крошки — одно слово. Сквозная грамматика workspace из `CLAUDE.md` действует полностью.

**Что игрок обязан видеть, не читая панель:**
- сколько ему положено и **откуда число** — метки Венеры, метки Юпитера, влияние (чтение
  `influence-yield` с разбивкой счёта уже существует — используй);
- **свои карты, способные нести флоатеры, настоящими премиальными лицами**, с текущим числом флоатеров
  на каждой — даже если такая карта одна;
- сколько он кладёт на каждую и **сколько осталось** разложить;
- чем подтверждение недоступно, пока разложено не всё (отключённое — с причиной, инвариант 5).

**Управление — существующая грамматика количества, новых глаголов нет.** Консоль уже говорит так в
амаунт-промптах `ConsoleTaskHost`: `bumperL` −1, `bumperR` +1, `triggerR` «максимум». Здесь:
d-pad — между картами; LB/RB — снять / добавить единицу **на карте в фокусе**; RT — положить на неё
весь остаток; A — подтвердить. LB на нуле и RB без остатка ничего не делают и не рекламируются как
доступные. Кнопки называются только семантикой и рисуются `GamepadGlyph` (инвариант 12). LB/RB в
Парламенте больше ничем не заняты — проверь, что в стадии НАГРАДА это остаётся так.

**Статус-строка в режиме раскладки** отвечает на два вопроса: что станет с картой в фокусе при текущем
k (ресурс `было → станет` и ПО по серверной таблице для этого k) и что в сумме — сколько осталось
разложить и общий сдвиг ПО по всем картам.

**Неполную раскладку отправить НЕВОЗМОЖНО — требование владельца, закрывается на каждом уровне, а не
одной отключённой кнопкой.** Игрок не должен иметь ни одного способа случайно отправить запрос, в
котором разложено меньше N.
1. **Старт с нуля.** Раскладка открывается с нулём на каждой карте. Никакого «всё на первую карту по
   умолчанию»: это одновременно автовыбор (инвариант 3) и заряженный случайный сабмит.
2. **Кнопка и её обработчик.** Пока остаток больше нуля, A в командной строке отключена с причиной
   («осталось разложить 2», инвариант 5), и **нажатие A в этом состоянии не делает ничего**: не
   отправляет, не дожимает, не переходит. Проверка стоит в обработчике нажатия, а не только в отрисовке
   кнопки.
3. **Ответ собирается только из полной раскладки.** Чистая функция, которая строит ответ, при сумме,
   отличной от N, возвращает «нечего отправлять», и до `gameTransport.submitInput` дело не доходит.
   Юнит-спек на неё.
4. **Сервер отказывает, а не падает.** Неполный или переполненный ответ отклоняется `InputError`,
   промпт остаётся стоять, частично не применено ничего: сначала проверка, потом применение.
   Сегодняшний `AddResourcesToCards` на этом месте бросает обычный `Error`; если механизм общий
   (§2.1), это чинится вместе с ним.

Переполнения тоже нет: RB без остатка и RT при нулевом остатке ничего не делают.

**Случайное A на входе в шаг.** В заседании A во время такта «дожимает» его, а шаг раскладки
открывается сразу после такта, так что A, нажатая, чтобы дожать, может прийти в только что открытый
шаг. Для раскладки это безопасно по построению пункта 1 — при пустой раскладке подтверждать нечего.
Для обычного выбора одной карты проверь, как себя ведёт RX01 сегодня: если A, пришедшая во время
предыдущего такта, может выбрать карту, закрой это для обоих режимов.

**Коммит.** Флоатеры летят с иконки на резолюции (`source: 'card-icon'` таблицы адресов) на каждую
выбранную карту, по одному, счётчик на карте тикает в кадре посадки, не раньше. Потом тело
возвращается к ряду партий. Отклонённый сабмит откатывает всё чисто.

**Семейство, а не новый экран.** Режим раскладки — член того же компонента выбора карты, поэтому его
получают не только резолюции: три карты проектов на `AddResourcesToCards` (Cyanobacteria, Communication
Boom, Philares) могут перейти на него же — это то решение по двум реализациям, которое требует §2.1.
Следующие резолюции с распределением — Greens Budget (животные и микробы разом), Medical Database
(микроб за каждую метку науки), Colonial Affairs — не должны строить свою поверхность. Не пиши их
механику сейчас, но и не закладывай в модель «ровно один тип ресурса», если это ничего не стоит.

**Вкус моушена Парламента в силе:** реагирует только то, чего коснулись; никакого мигания и
одновременных подсветок; подпись не опережает объект; источник и цель видимы на всём полёте.

### 2.3 Первая резолюция Союза: четвёртая партия и впервые Союз у власти

**Дыра первого поколения становится достижимой.** Промт-фикс итогов (Ф4) установил: пока в колоде
карты ровно трёх партий, стартовый правитель всегда представлен в области. С Cloud Development в
Venus-партии колода — это четыре партии, и в первом поколении область может сложиться без Зелёных.
Тогда Зелёные правят по напечатанному слоту, а на картах не представлены — сервер начисляет им
поддержку как отсутствующей партии, при этом гнёзда на плитке правителя скрыты. Спек
`ParliamentPhase.spec.ts § THE STARTING-RULE RULER` упадёт именно в этот день.

- **Правило сначала сверь с рулбуком** (сетап: что стоит в слоте ENACTED в начале; шаг народной
  поддержки: «not present on any card in the Voting Area or Enacted slot»). Буквальное прочтение, по
  которому сервер работает сегодня: напечатанный слот — не карта, значит стартовый правитель поддержку
  получать может. Если рулбук говорит иное — это решение владельца: остановись на этом пункте и опиши
  его, сервер молча не меняй.
- При буквальном прочтении правка клиентская: гнёзда на плитке правителя скрываются по признаку
  **«партия ПРИНЯТОЙ КАРТЫ»**, а не по флагу `ruling`; то же условие исключает партию из строки
  поддержки в итогах. Стартовый правитель без карты показывает свои гнёзда и свой запас. Спек
  переписывается под точную формулировку.

**Союз у власти не был отрепетирован ни разу.** В каталоге не было ни одной его карты, даже среди
dev-примеров (финальная полировка записала это как открытое). Теперь Союз может править. Проверь путь
целиком: плитка Союза на месте правителя, эффект правящей партии для всех, её реакции в записях
выплат, действие «Торговля с Союзом» в «Действиях карт» (Colonies в Redux обязательны; решения Q-6 —
свободный флот, занятость колонии, бесплатность торговли, необязательный шаг трека вопросом). Добавь
Союз в репетицию семейств («Полигон», галерея) — закрыть этот хвост и есть часть задачи.

С четырьмя партиями область из трёх карт становится нормой, а не исключением. Прогони обновление по
журналу на этом составе — сценарии из `ParliamentRenewal.spec.ts` на четырёх партиях.

## 4. Пробники и спеки

Пробник утверждает видимость источника и цели и движение между ними; пробник факта считается
отсутствующим.

**Сервер:**
1. N = Венера + Юпитер + влияние по каноническому счётчику; карта с обеими метками даёт 2.
2. Форма шага: `N = 1` или одна карта — обычный выбор карты (`resourceGainPrompt`, без автовыбора);
   `N ≥ 2` и карт `≥ 2` — распределение. Сумма ровно N; применение через `addResourceTo`; один `report`
   со списком целей.
3. Таблица ПО распределения: для каждой карты и каждого k совпадает с тем, что даст реальное применение
   (спек на карте со ступенчатыми ПО за флоатеры).
4. Пропуски: N = 0; ни одной карты для флоатеров — с величиной.
4а. Неполный и переполненный ответ: `InputError`, промпт стоит, ничего не применено.
5. Возобновляемость: перезагрузка посреди распределения пересобирает промпт, ничего не применено дважды.
6. Задание председателя не растёт от флоатеров резолюции.
7. Без Venus карты нет в колоде; со старым сохранением Venus-партии всё загружается.
8. Первое поколение с четырьмя партиями: область без Зелёных — поддержка стартовому правителю по
   принятому прочтению правила.

**Клиент:**
1. Встроенный шаг: резолюция слева видима на всём шаге, тело — распределение, ряд партий ушёл движением,
   ни одного кадра пустого тела; лента не изменила высоту.
2. Все подходящие карты видимы настоящими лицами, включая случай одной карты; при `N = 1` на экране
   ровно тот компонент выбора, что у RX01.
3. Раскладка: открывается с нулём на каждой карте; LB/RB меняют счётчик карты в фокусе, RT кладёт
   остаток, LB на нуле и RB без остатка ничего не делают; статус-строка показывает ресурс и ПО карты
   в фокусе для текущего k и общий итог.
3а. Неполная отправка невозможна: при остатке больше нуля A отключена с видимой причиной, а нажатие A
   **не порождает ни одного запроса** — пробник считает запросы к эндпоинту ввода, их ноль. A, нажатая
   во время такта перед шагом, не подтверждает ни раскладку, ни выбор одной карты.
4. Полёт: каждый флоатер стартовал с иконки резолюции, сел на свою карту, счётчик карты тикнул на посадке;
   источник и цель видимы.
5. Плитка стартового правителя в первом поколении показывает свои гнёзда и запас; правитель с принятой
   картой — не показывает.
6. Союз у власти: плитка на месте правителя, его эффект и действие доступны, записи выплат с реакцией.
7. Лицо: зависимость от Venus видна; формула совпадает со сканом по составу членов.

Обязательный e2e — один: распределение на две карты с коммитом и полётом, Venus-партия, четыре партии.

## 5. Регрессия

Глазами и кадрами, три профиля, Deck отдельно: RX01 (выбор одной карты — особенно если перевёл его на
общую поверхность), RX05 (встроенный добор), заседание без выбора, обновление на четырёх партиях,
осмотр резолюции, «Полигон» и галерея с Союзом, партия без Venus целиком.

## 6. Режим работы

Экономный: юниты плюс пробники раздела 4, только они. Коммит на блок (A сервер и модель · B встроенный
шаг · C Союз и первое поколение · D арт, лицо, локаль, пробники), каждый зелёный по юнитам,
`npm run lint`, `npm run build:test`. **Не пушить.** Документ карты — `docs/TURMOIL_REDUX_CLOUD_DEVELOPMENT.md`
по образцу RX01–RX05; журнал — `docs/claude/parliament-sitting-progress.md`. Если в ходе работы
механизм распределения оказался общим, опиши его в чеклисте автора как новую строку семейства — это то,
чем воспользуются следующие карты.

В отчёте: форма промпта и исхода распределения, решение по `AddResourcesToCards`, раскадровка шага с
замерами, ответ по правилу первого поколения со ссылкой на страницу рулбука, что проверено в пути
«Союз у власти», список новых ключей i18n.

## 7. Нельзя

Класть флоатеры самим, если у игрока одна карта. Предзаполнять раскладку. Давать хоть одному пути
отправить неполную раскладку. Отвечать на неверную сумму падением вместо `InputError`. Распознавать промпт по заголовку. Заводить новый вид
исхода там, где достаточно расширить `cardResource`. Две параллельные реализации распределения без
решения. Особую ветку счёта «для одной карты» вместо члена семейства. Отдельный экран вместо шага в
теле. Тело, меняющееся во время движения по столу. Молча менять серверное правило первого поколения.
Литералы кнопок. Мигание. Пуш и красные коммиты.
