## Energy → Heat conversion transition (end-of-generation paired delta)

The end-of-generation rule "all of a player's energy turns into heat" (and the **Supercapacitors** player-chosen-amount variant) is surfaced as a premium micro-interaction so the player *sees* the energy MOVE into heat rather than two counters silently jumping: the energy cell pulses electric-blue (source), the heat cell pulses warm (target), a premium sci-fi **transfer glyph** (chunky filled chevron-arrow with body/inner-tip/travelling sweep/directional bloom — NOT a thin line) runs energy → heat anchored STRICTLY between the two ICON rects (rotated to the energy→heat vector, scaled to the inter-icon gap so it never overlaps the icons or counters), the paired `DeltaChip`s (`−X` energy / `+X` heat) float beside the cells, and both counters interpolate (energy down, heat up) in lock-step. It is a **transition gate**: while it plays, the next-phase modals (research / draft / `MandatoryInputModal`) and the endgame screen are blocked — they all key off the held `playerView`.

**The SERVER is the source of truth for the converted amount — a client diff cannot be.** In `Player.runProductionPhase` the conversion (`heat += energy; energy = 0`) runs BEFORE `finishProductionPhase` adds production income to BOTH energy and heat, so a before/after-production diff can't isolate the converted amount. So the server snapshots `IPlayer.energyHeatConversion = {amount, energyBefore, heatBefore, generation}` (`src/common/models/EnergyHeatConversionModel.ts`) at conversion time — transient, self-only, cleared on the next input in `Player.process`, exactly like `lastReveal`; serialized into `PlayerViewModel.energyHeatConversion` in `ServerModel.getPlayer`. The non-Supercapacitors path sets it inline in `runProductionPhase`; Supercapacitors sets it in its `andThen` (the chosen amount). Both capture the PRE-conversion stocks (production is added afterwards). Guarded by `tests/server/EnergyHeatConversionSnapshot.spec.ts` + the Supercapacitors spec.

**The gate REUSES the existing `holdingForMarker`/`holdingForTilePlacement` pattern in `WaitingFor.vue` — it is NOT a new mechanism.** The reactive controller `src/client/components/feedback/energyConversionTransition.ts` owns the animation: `energyConversionState` (the panel counter override + the overlay read it), the rAF interpolation, the dedup `seen`-set (`${color}:${generation}` — poll replays of the same view never re-animate), the change-feedback baseline seeding, and the gate `Promise` (with a safety timeout so a backgrounded-tab rAF freeze can never hang the gate forever). The PURE detect / duration / interpolation maths live in the sibling `energyConversionModel.ts` (`readConversionEvent` / `shouldAnimateConversion` / `conversionDurationMs` = `clamp(1100 + amount*45, 1200, 2200)` — small ~1200 / medium ~1400-1700 / large caps 2200, reduced-motion → 480ms / `interpolate`), unit-tested under the server runner (`tests/client/components/feedback/energyConversionModel.spec.ts`). The arrow geometry (`EnergyConversionOverlay.vue`) anchors to `[data-conversion-icon="energy"/"heat"]` (the ICONS, for the glyph) + `[data-conversion-cell=…]` (the cells, for the chips); a ray-box-exit + adaptive safe-gap computes the free span between the icon edges, rotates a down-authored glyph to the vector, and shrinks (`--ec-arrow-scale`, compact fallback) when the single-screen panel packs the rows tight (~10px between icon edges). BOTH commit paths call the same trio — `detectEnergyConversion(prev, next)` → `await runEnergyConversion(event)` → commit → `nextTick(endEnergyConversion)`: `WaitingFor.fetchPlayerInput` (the viewer's own pass that ends the generation; adds `holdingForConversion` to the empty-render `v-if`, and `isServerSideRequestInProgress` stays raised through the await) AND `App.update` (the POLL path — how a non-last-passer's own conversion arrives; guarded by `isEnergyConversionActive()` so a concurrent poll can't commit mid-animation). `detectEnergyConversion` claims the dedup key synchronously, and `runEnergyConversion` flips `active` synchronously, so the two paths can't double-fire.

**Anti-double-count seeding.** After the animation, `runEnergyConversion` calls `changeFeedbackManager.setBaseline(scope, 'energy.stock' / 'heat.stock', after)` (a new manager method) so the NORMAL `AnimatedMetricValue` stock chips that fire on the commit show only the production REMAINDER (e.g. `+3` energy / `+4` heat), not the full pre-conversion net (`−5` energy / `+12` heat) — which would visually contradict the `−X` / `+X` the conversion just told. Scope = `${runId}|${color}`, matching `AnimatedMetricValue.computeFullScopeKey`.

Client surfaces: `EnergyConversionOverlay.vue` (App-level, sibling of `RevealResultOverlay`; draws the arrow + floating chips from `[data-conversion-cell="energy"/"heat"]` rects, re-measures on resize/scroll, **graceful no-op when the cells aren't on screen** — e.g. the viewer is inspecting an opponent — the gate still resolves), `PlayerResource.vue` (when `energyConversionState.color === scopeKey` and the row is energy/heat: shows the interpolated override + the `resource_item--conversion-source/-target` highlight + the anchor attr; `AnimatedMetricValue` still binds `:value="count"` canonical, NOT the override). Styles `src/styles/energy_conversion.less` (`@import` in `common.less`); `prefers-reduced-motion` honoured (short highlight, no chevron travel / counter glide); no native `title`. **Documented frontier:** only the VIEWER's own conversion animates (the field is on `thisPlayer`); opponent conversions are a deliberate phase-2 (the controller/overlay are structured to extend to `PublicPlayerModel`). **To add a new resource-conversion** (a future card / expansion), reuse the same pipeline: snapshot the amount + pre-stocks server-side onto the view, and `readConversionEvent` + the overlay generalise from there.

### The console CONVERSION PROMPT (Supercapacitors' amount — 2026-08-15 rework)

The Supercapacitors `SelectAmount` renders in console native as a **premium compact conversion prompt** inside `ConsoleTaskHost`'s amount branch, keyed STRUCTURALLY off the model's `conversion` hint (never the title). Pieces:

- **`src/client/console/conversionPromptModel.ts`** (pure, spec'd in `tests/client/components/console/conversionPromptModel.spec.ts`): both sides' `current → after` + signed deltas for the dialed value (mirrors exactly the server's `andThen` math — no second formula), the NEUTRAL verdict (value 0 → no deltas, no gain accent, «Без изменений»), the BINARY verdict (`min 0 / max 1` renders as two choice plates, not a dial — «THE INSTRUMENT FOLLOWS THE BUDGET»), the recognised-shape headline (`Energy conversion` for stock energy→heat) and the commit verb (`Do not convert` / `Convert ${0}` — a zero commit is a stated refusal, never «ОК»).
- **Header**: kicker «ЭФФЕКТ ПРОИЗВОДСТВА» (`consoleTaskSummary` — conversion hint + `Phase.PRODUCTION`, structural), headline replaces the server title, the ask demotes to the subtext; the server marks `choiceContext` (`Supercapacitors.onProduction` → `namedCardEffect`), which lights the compact source dock, `L3 Источник` and the deferred chip's source for free.
- **Command bar**: the commit verb sits on **A** (`confirm` — a dial has no select step, so A is the decisive press; X stays a silent alias); the LB/RB/RT hints live ONLY in the bar (the in-panel `__stepper-keys` copy is gone). A conversion opens at **0** even under `maxByDefault` — converting is a deliberate opt-in and the verb names the refusal.
- **Commit handoff** (the sequencing the rework exists for): submit → commit-lock (`submitting` guards re-entry; `adjust`/`maxOut` refuse; a 200 ms transform-only press pulse) → the response arms `runEnergyConversion(event, {leadInMs})` — `WaitingFor` passes `motionMs(320)` exactly when console mode is on AND the outgoing prompt was an amount — → `energyConversionState.active` flips synchronously, the task host's `v-if` (ConsoleShell) drops it, its leave plays during the **lead-in** (`state.leadIn`: gate closed, counters held at the pre-values, overlay unmounted) → the shade lifts → the EXISTING rail transition plays on a fully readable rail → the view commits after the gate. Zero conversion writes NO server snapshot → no ceremony, the prompt just leaves.
- **Rail focus**: while the prompt is live, `conversionPromptUi` marks the two stock rows (`con-res__row--conv-watch`, a neutral rim, values untouched); the transition's own source/target highlight replaces it past the commit.
