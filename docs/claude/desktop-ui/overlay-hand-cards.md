## Cards-in-hand overlay (the "КАРТЫ В РУКЕ" overlay + unified play flow)

The bottom-bar **Cards** button (`activeOverlay === 'cards'`) opens `src/client/components/handCards/HandCardsOverlay.vue` for the viewer's OWN seat — a premium glass/HUD board that REPLACED both the legacy flat `bar-overlay--cards` `SortableCards` list AND the legacy "play a project card" radio form. Viewing another player's seat still falls back to face-down card-backs × their hand count (the server never sends opponent hand contents). It shares the visual language of `PlayedCardsOverlay` / journal / VP (glass frame, L-corner ticks, Prototype-font header, filter chips). NOT in `PLACEMENT_LOCKED_SELECTORS` itself (it's a view overlay) — but the РАЗЫГРАТЬ buttons inside it ARE (`.hand-card-play-btn`).

**The overlay shows the WHOLE hand** (`playerView.cardsInHand` — project cards), not just playable ones: playable cards bright with an active **РАЗЫГРАТЬ**; unplayable cards dimmed (grayscale/brightness, like draft/select disabled cards) with a disabled button that reveals a custom premium reason popover on hover/focus (NO native `title` tooltip).

**Self-replicating Robots hosted cards ride this overlay too** — they're the ONLY way to play them in the modern UI. A card linked to SRR isn't literally in hand, but the game lets the player play it from there (the server's `getPlayableCards()` includes `card.targetCards`, with the cost reduced by the resources on it). So `PlayerHome.handOverlayCards` = `stagedCardsInHand` **concatenated with** `thisPlayer.selfReplicatingRobotsCards`, and THAT (not `stagedCardsInHand`) is the overlay's `:cards`. The hosted-card models are built by `ServerModel.getSelfReplicatingRobotsTargetCards(player, modelIsForThisPlayer)` through the shared `cardsToModel` (so they carry `isSelfReplicatingRobotsCard`, the resource count, the DISCOUNTED `calculatedCost`, and — only on the viewer's OWN model — `unplayableReasons`, so an unaffordable hosted card reads as a proper rules block, not a misleading "not your turn"). `HandCardItem` flags each with a teal `.hand-card-item__robot` pill (absolute → no grid reflow; label "Роботы" + the `−N` discount + a premium tooltip "На «Роботах саморепликантах»…"). РАЗЫГРАТЬ works unchanged — `onPlayHandCard` looks the card up in `playProjectCardAction.input.cards` (which already includes hosted cards), so the payment modal → submit flow is byte-identical. Hosted cards are kept OUT of `cardsInHandCount` (the hand-count badge stays the true hand size) and are EXCLUDED from the overlay's `displayCards` in sale (Sell patents) / mandatory-select / client-pick modes (you can't sell or be asked to discard a hosted card). Covered by `tests/models/ServerModel.spec.ts`.

**Source of truth for "playable now" AND for the reasons is the server.** The enabled state of РАЗЫГРАТЬ is gated STRICTLY by membership in the server's `Play project card` action list — `PlayerHome.findPlayProjectCardAction` walks `waitingFor` for the `projectCard`-type option titled `'Play project card'` (Player.ts action menu, `SelectCardToPlay.ts` title), and `playableProjectCardNames` is the set of names in its `cards` array. So the button can never offer an illegal play.

**Structured unplayable reasons are computed authoritatively on the server** (replacing the old client-side derivation). `src/server/models/unplayableReasons.ts` (`unplayableReasons(player, card)`) reuses the REAL playability logic: it calls `player.canPlay(card)` as the gate (returns `[]` when playable), then collects a structured `UnplayableReason[]` (`src/common/cards/UnplayableReason.ts`) from (a) each unmet `CardRequirement.satisfies` — recompiling `card.requirements` and mapping by `RequirementType` to a reason with the current value via `InequalityRequirement.getScore`; (b) `player.affordabilityDeficit(card)` (a new read-only `IPlayer` method mirroring `canAffordInternal`, returns the M€-equivalent gap); (c) the board placement / target checks `Executor.canExecute` runs (`getAvailableSpacesForType`, `filterSpacesAroundRedCity`, moon spaces, `canHaveProductionReduced`, `getPlayableColonies`, `production.canAdjust`, delegate count); else a generic `rule` fallback. Capped at 5, de-duped, read-only. It's attached to each **own-hand** card model via the `unplayableReasons: true` option to `cardsToModel` (only at `ServerModel` line ~176, `cardsInHand`) → `CardModel.unplayableReasons`. The reason `type`s: `megacredits / globalParameter / tr / tag / production / count / party / placement / target / phase / turn / rule / generic`. `turn` / `phase` are the EXCEPTION — added client-side, because the server can't know whose turn it is when serializing a card in isolation. Reason messages are English i18n templates translated client-side; new keys live in `ru/ui.json`.

**Be specific, never bare-generic where a value exists.** `requirementReason` maps EVERY numeric `RequirementType` (oxygen/temp/venus/oceans/tr/tag/production/cities/colonies/greeneries/floaters/resource-types/moon rates+tiles/corruption/underground-tokens/party-leaders) to its own labelled message + `current` value (via `InequalityRequirement.getScore`) — so e.g. "floaters" reads "Требуется аэростатов: 5 / Сейчас: 0" exactly like "oceans", not the generic fallback. Target reasons are likewise specific: `decreaseAnyProduction` names the resource via its icon ("Некому снизить производство ⟨heat⟩"), `buildColony` → "no colony to build on". For blocks that live in **bespoke `canPlay`** (which the generic checks can't introspect), `ICard` exposes an opt-in `unplayableReason?(player)` hook — implemented on `RoboticWorkforceBase` ("no building card to copy") — that the explainer calls in the fallback branch before the last-resort generic `rule` line. Add the hook to other bespoke cards as needed instead of widening the generic message. Visually the popover groups reason types by accent: requirement family (params/tr/count/tag/production) = cyan, cost = gold, placement = orange, target/party = purple, turn/phase/rule = grey.

Framework (`src/client/components/handCards/`):

- `handCardModel.ts` — flat entry building (`buildHandEntries`, NO type grouping unlike played-cards), filter (`filterHandEntries`), sort (`sortHandEntries` — availability/cost/type/tag/name), and **faceted** chip data. Each chip builder shows a faceted count = apply every dimension EXCEPT its own group (the standard faceted-search rule, so a group never zeroes out its own options): `buildAvailabilityChips` keeps type+tag and varies availability (All/Playable/Unplayable counts within the current type+tag slice); `buildTypeChips` keeps availability+tag; `buildTagChips` keeps availability+type. The stable `FILTERABLE_TAGS` / `HAND_TYPE_DEFS` order means an active-empty chip never jumps position. **NO SILENT-LOSS for `addResourcesToAnyCard` — the systemic "no eligible card" warning.** An on-play (or action) effect that adds a card-resource to ANY of the player's cards (`addResourcesToAnyCard`) does NOTHING when the player owns no card that can hold it (e.g. Eos Chasma National Park's +1 animal with no animal-holding card in play) — upstream resolves it server-side and the resource just evaporates. To make this NEVER silent, the preview builder (`src/server/models/actionPreview.ts`) probes the REAL candidate set via `new AddResourcesToCard(player, type, {restrictedTag, min, robotCards}).getCards()` (helper `addAnyCardCandidates`) and, when it's empty, (a) SUPPRESSES the misleading `+N to a card` result chip in `effectsForBehavior` and (b) emits a `{kind:'note', noteKind:'warning', text:'No eligible card — this resource is not added.'}` step in `stepsForBehavior`. **This one builder change covers ALL ~56 `addResourcesToAnyCard` cards at once** (VenusSoils etc. — not just the named ones) — declarative cards need no per-card hook. **`addResourcesToAnyCard` is single-OR-ARRAY** (`AddResource | Array<…>` — Imported Nitrogen adds 3 microbes AND 2 animals); BOTH walkers normalize via `addToAnyCardList` and emit a chip + picker (or warning) **per addition**, in `Executor` defer order, so a multi-addition card never silently drops a chip + pick (the bug: the old `!Array.isArray` guard skipped the whole array block — modal showed only plants/TR, no microbe/animal pickers). Guarded by `cardPlayPreviewCoverage.spec.ts`'s "surfaces EACH addResourcesToAnyCard addition" test (counts the surfaced steps per in-scope declarative card vs its addition count) so the array (or any future per-addition) drop can't regress. **Each add-resource pick names its resource via the ICON** (the step carries `cardResource` — the icon key; the modal picker prompt shows `[microbe] ×3`, language- and grammar-safe, never a text resource name) so a side-by-side multi-resource pick (microbes vs animals) is unambiguous about WHICH picker is for WHICH resource. **`stepPromptText` TRANSLATES + SUBSTITUTES the title's data tokens** (`translateMessage`, not the raw `.message`) — a `message('Select card to add ${0} ${1}', …)` title must render the count/resource, never the literal `${0} ${1}` placeholders (the bug: the modal showed the raw template; the РАЗЫГРАНО pick-strip's `pickTitleText` already substituted, the modal prompt didn't). The `'warning'` noteKind is a member of the `ActionPreviewStep` note union (`src/common/models/ActionPreviewModel.ts`) and renders as a distinct ORANGE block (`⚠`, above the neutral notes) via the ONE shared `SkippedEffectWarning.vue` — mounted by `HandCardPaymentContent.vue` (play modal) and `ActionNextStepNotice.vue` (action details + confirm), and mirrored in the console composers (`ConsolePlayCardConfirm` / `ConsoleActionComposer`, `.con-composer__warn`). **A WARNING MUST NAME WHICH EFFECT IS SKIPPED — never a bare "no valid target".** A card commonly has SEVERAL effects (Asteroid: +temperature, +titanium, remove 4 plants) and a skipped ATTACK has NO chip in `effects` (it changes an OPPONENT's pool, not the player's), so the warning is that effect's ONLY mention — an anonymous reason line leaves the player unable to tell what they just lost. So every warning carries `skipped: {label, effect?}`: `label` is an English i18n key NAMING the effect (the shared `actionPreviews.SKIPPED_LABEL` set — `removePlants` / `removeResources` / `stealResources` / `reduceProduction` / `removeAnimalsOrPlants` / `addToCard`; reuse it, don't coin a per-card phrasing), and `effect` is the magnitude it WOULD have applied, rendered as a MUTED, struck-through `ActionEffectChip` (`:skipped="true"`) so it can never read as something that happened. **`effect` is OMITTED when no single magnitude is honest** — an either/or attack (Sabotage 3 titanium OR 4 steel OR 7 M€; Virus 2 animals OR 5 plants; VenusianPlants microbe OR animal) shows the label alone rather than inventing a number. Producers: `actionPreviews.warningNote(text, {resource?, skipped})` / `targetStepOrWarning(player, step, text?, skipped)` (+ `skippedAttackChip(icon, amount, 'production'?)` for the opponent-facing chip) — build warnings through these, never a hand-rolled `{kind:'note', noteKind:'warning'}` literal (that path shipped a raw `CardResource` as the icon key → `card-resource-Animal`, no sprite). Client side ONE pure derivation, `skippedEffectView.ts` (`isSkippedWarning` / `skippedEffectView` / `skippedEffectViews`), feeds every surface, so they can't diverge; an un-annotated legacy warning degrades to the reason line alone. **NO SILENT-LOSS for a VARIABLE amount that counts to ZERO — the second half of the same rule.** `effectsForBehavior` used to DROP any `stock` / `production` / `tr` / `drawCard` chip whose amount computed to `0`. For a printed number that is dead code (no card declares a 0); for a `Countable` OBJECT read from live game state it deleted the card's headline clause exactly when the player most needed it. Toll Station («+1 M€ production per space tag your OPPONENTS have») previewed as nothing but its own tag against a bot with no space tags: «I get nothing right now» became indistinguishable from «this card has no production clause», on the screen whose entire job is to prevent that. **Zero is the answer, not the absence of one** — a variable amount is now always reported, and `ActionEffectChip` renders it muted with the existing `no effect` note (`current === resulting`; the note and «no effect» are BOTH shown now — `noEffect` used to REPLACE the note, which made a zero PRODUCTION chip identical to a zero STOCK chip of the same resource). A pool-less zero («+0 to a card», «draw 0») is muted on `amount === 0` since it has no `current` to compare. **The BASIS is what makes a zero legible** (`ActionEffect.basis`, now a LIST of `{count, label, tag?}` terms): each counted entity is counted ON ITS OWN and labelled with its SCOPE — `Your tags` / `Tags in play` / `Opponent tags` (+ the counted tag's ICON, so one key per scope instead of one per tag), `Your colonies` vs `Colonies in play`, `Your cities` vs `Cities`, plus floaters / Moon rates+tiles / Underworld counts. Two bugs fixed by the list shape: a composite countable (`{cities, colonies}` — Molecular Printing) took its LABEL from the first key while counting the SUM (reporting a city count the board did not contain), and `{colonies}` vs `{colonies, all}` were both labelled «Colonies» although one counts yours and the other everyone's. The rate (`each` / `per`) is deliberately NOT applied to a basis count — the basis says WHAT was counted, the chip's amount is the result. **Guard: `tests/models/variableAmountPreviewGuard.spec.ts`** sweeps every in-scope card (project `behavior` + blue-card `action`) at a fresh-game state where the counts ARE zero and fails naming the exact cards that lose a declared clause — it caught 18 on-play clauses plus the action cards when the guard was written. Related same-class fix: the console composer's copy-production fold (`consolePlayCardComposer.ts`) dropped a resource whose base chip and copied chip CANCELLED to zero, deleting the whole energy story from a Robotic Workforce result; a resource the fold actually touched now stays on screen at 0.
