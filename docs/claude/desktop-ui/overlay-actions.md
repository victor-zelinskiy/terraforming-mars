## Actions overlay (the "ДЕЙСТВИЯ" overlay — activatable blue-card / corporation actions)

The bottom-bar **ДЕЙСТВИЯ** button (`activeOverlay === 'actions'`) opens `src/client/components/actions/ActionsOverlay.vue` — a premium **MASTER-DETAIL** surface (the interactive sibling of the Effects overlay). It REPLACED the legacy `bar-overlay--actions` flat `<Card>` list AND the earlier flat-grid-of-action-blocks-with-ВЫПОЛНИТЬ rework. **LEFT** = a compact 1–3-column grid of action GROUP cards (`ActionGroupCard.vue`: a SLIM header — name + type chip + stored-resource badge + group status — then one selectable `CompactActionCard.vue` ROW per render node, so a 2-action card is exactly the slim header + two compact rows tall, no per-row button). **RIGHT** = a static details panel (`ActionDetailsPanel.vue`) for the SELECTED action: source identity + ⤢ fullscreen, the FULL action text, the cost/result breakdown (`ActionResultsPreview.vue`), constraints (the can't-act reason), stored-resource count, "what happens next" (`ActionNextStepNotice.vue` variant `next` = «Далее»), and a **context-aware CTA** that OPENS the confirmation modal (never executes). Selecting a row in the master only FOCUSES the action (it never submits) — only the details CTA acts. Keyboard nav (Arrow keys move the selection across `flatRows`, Home/End, Enter/Space = CTA, Esc = close). Shows ALL actions — available / unavailable-with-reason / activated-this-generation — behind two faceted filters; nothing is silently hidden. Same premium dark-glass HUD frame + fullscreen. The two buttons are deliberately ADJACENT in the bottom-left rail (Cards · **Actions · Effects** · Played · VP) so the pair reads as passive (Effects) + activatable (Actions) abilities. (The old flat-block `ActionBlock.vue` is DELETED; the branch↔node helpers live in `actionBranchView.ts`.)

**The SELECTION is a RENDER NODE, the BRANCH is resolved from it — never a positional index.** Master rows are render nodes (`group.nodes`, manifest order); the preview's branches are in the server's BEHAVIOR order, and the two can DIFFER (Regolith Eaters / Atmo Collectors print "add" first but the server lists "spend" first). So `selectedKey`/`nodeIndex` identify a NODE, and both the details panel and the confirm modal resolve the matching preview branch via **`branchPositionForNode(group, branches, nodeIndex)`** (`actionBranchView.ts`) — which runs the SAME token-overlap match (`assignBranchNodes`) the modal graphic uses, then INVERTS it (which branch claimed this node). A naive node-i→branch-i map SWAPPED a multi-action card's «будет списано»/«вы получите» between its two actions — `branchPositionForNode` is the fix (guarded by `tests/client/components/actions/actionBranchView.spec.ts`). A combined-node card (1 node draws all branches, e.g. Self-Replicating Robots) resolves to `undefined` → the modal's in-modal branch picker. `PlayerHome`'s activate payload + `pendingCardAction` carry `nodeIndex` (not a branch position); the modal re-resolves from its own preview.

**Multi-action (`or`) rows read CLEAN — the leading "ИЛИ" is stripped, the alternation is a deliberate divider.** A multi-row group is ALWAYS an `or` action (a card has ONE action that branches). Each row's graphic has its leading OR connector stripped (`stripNodeOr`, `actionBranchView.ts`), and `ActionGroupCard` renders a slim `.action-group__or` "ИЛИ" badge BETWEEN consecutive rows — so the row graphic is never polluted by a stray "ИЛИ" symbol (the old leakage) while the choose-one semantics stay explicit.

**Selected state is on the ROW, not the group.** `.compact-action--selected` is the strong cyan ring; `.action-group--selected` is only a SUBTLE rim (the group merely CONTAINS the focused row) — so a 2-action card never reads as if BOTH actions are chosen.

**The master uses CSS MULTI-COLUMN packing, NOT a uniform grid** (`.actions-board__master { column-count: var(--actions-master-cols); column-fill: balance }` + `.action-group { break-inside: avoid; margin-bottom }`). A grid forces every row to the tallest card in it, so a 1-action card stranded beside a 2-action card kept a tall EMPTY gap below it — wasting space and forcing scroll even when the cards would otherwise fit. Multi-column packs each column independently and balances heights, so a 1-action card takes exactly one compact row's height and a 2-action card two — deterministic column-major order (NOT chaotic masonry), tight, scroll only when the content genuinely overflows. Because the layout is column-major, keyboard nav is Down/Up = ±1 (the next DOM item IS visually below) and Left/Right = ±`ceil(rows/cols)` (one column over).

**Double-click a row = quick-activate** (`CompactActionCard` `@dblclick` → `ActionGroupCard.activateRow` → overlay `@activate` → `PlayerHome.onActivateCardAction`). ONLY for an AVAILABLE action — `activateRow` no-ops otherwise, so a double-click on an unavailable action just leaves it selected with its reason shown, never opening a modal the player can't act on. Single-click still only selects. `onActivateCardAction` also guards on `placementPending` (the double-click is a separate path the `PLACEMENT_LOCKED_SELECTORS` CSS/JS guard — which only covers `.action-detail__cta` — can't catch).

**The details panel shows a "За партию" (This game) USAGE summary — the active-action twin of the Эффекты overlay's per-effect stats (event/stat foundation; see `docs/EVENT_STAT_FOUNDATION.md`).** Blue-card / corp / CEO actions are ALREADY recorded under their `beginAction` scope (category `card-action`/`corporation-action`/`ceo-action`), so this is AGGREGATION + UI, not new recording — the ONE recording change was stamping the root-action `category` onto the `GameEvent` (`GameEvent.category`, previously only in the recorder context for the journal log) so `aggregate.actionStatsBySource` can tell a card's ACTION usage apart from its on-PLAY gains (both are `beginAction` roots with the same card source). `actionStatsBySource(events, owner)` folds each action chain's OWN output (events sourced to the action card or sourceless-inherited — NOT nested other-card passive effects) into per-card `SourceStats`; `actionOverlayStats` is the per-player projection, served by `/api/game/action-stats` (`ApiGameActionStats`, the twin of `ApiGameEffectStats`). The pure view-model `actionUsageSummary.ts` (`getActionUsageSummary(stat)`, unit-tested under the server runner like `effectSummary`) classifies the action by value KIND (`resource`/`conversion`/`draw`/`terraform`/`usage`) → a headline + impact lines (reusing `effectSummary.genericLines`) + activation count + last-used generation + a confidence chip; an unused action shows "Действие ещё не активировалось…", never a dead state. `ActionsOverlay` fetches the stats stale-while-revalidate (cached by colour in `actionsOverlayState`, keyed by `statsCacheKey`=generation), passing the selected card's stat to `ActionDetailsPanel` (+ the hidden height-probes, so the stable split size includes the section). Recording + aggregation are GENERIC → EVERY action card is covered automatically (no per-card work); an activation-only action shows the count with `ruleOnly` confidence. Guards: `tests/events/actionStats.spec.ts` (aggregation + the play/action split) + `tests/client/components/actions/actionUsageSummary.spec.ts`.

**The details panel leads with the DESCRIPTION; the source card is SECONDARY.** `.action-detail__desc` is the largest/brightest body text (14.5px) — the key "understand the action" block — and `.action-detail__source-card` is kept small (`zoom: 0.46`, click to enlarge). An UNAVAILABLE selected action shows a prominent `.action-detail__status` ALERT (glyph + heading + the EXACT reason via `statusHead`/`statusText`, which joins ALL the server's rules reasons so every case is covered), not a faint line — the disabled CTA is never the only signal. The alert is colour-coded by KIND: **`--rules` (a hard block — can't afford / conditions / no target) is RED** (glyph `✕`), `--soft` (timing — not your turn) is amber (`⏳`), `--activated` (used this gen) is blue (`✓`). The grid groups read clearly different too: `--rules` gets a RED rim + badge + accent bar, `--soft` amber, `--activated` blue, all desaturated/dimmed — so availability is obvious at a glance, not only after opening details.

**PER-BRANCH availability — a multi-action card can have ONE branch unavailable while its sibling is playable** (e.g. Rotator Impacts: "add an asteroid" is affordable, "spend an asteroid → Venus" needs a resource on the card). The card-level state is `available` (it's in the server's available list because ≥1 branch is playable), so marking the WHOLE card available was wrong — the blocked branch looked actionable, the only signal being the disabled CTA. The fix is CLIENT-side, reusing the preview: each `ActionPreviewBranch` already carries `available` + `unavailableReason` (+ now `unavailableReasonParams`, the only server tweak — `actionPreview.ts` passes the reason's params so a deficit like "Need 3 more M€" renders). `ActionsOverlay.prefetchBranchPreviews()` silently prefetches the previews of MULTI-node available cards (single-action cards don't need it — their row availability IS the card-level state); `ActionGroupCard` gets the `preview` and computes PER-ROW `rowStatus(i)`/`rowReason(i)` via `branchPositionForNode` → an unavailable branch row renders `--rules` (red-rimmed/dim + the reason tooltip), `activateRow` no-ops on it (double-click can't open a modal for a blocked branch), and `ActionDetailsPanel` shows the RED branch-level alert + a disabled CTA. So a blocked branch is unmistakable in the grid AND explained in details.

**The overlay SIZE must NOT jump when switching the selected action, AND no detail should scroll while there's screen space.** The details panel's content varies per action (description length, result chips, source card, unavailability alert), which used to grow/shrink the split row → the overlay re-sized on every selection. FIX (two parts): (1) the detail is `position: absolute; inset: 0` inside a relative `.actions-board__detail-cell`, so its content height NEVER contributes to the split row height — the detail's OWN content scrolls (`.action-detail__scroll` flex-1 + overflow) with the CTA pinned below (`.action-detail__cta-row` flex-shrink:0); the master uses `align-self: flex-start`. (2) the split height is PRE-COMPUTED for the TALLEST detail at the current action set via a HIDDEN MEASURER (`.actions-board__measure` — one card-LESS `ActionDetailsPanel :measuring="true"` per action ROW, rendered `visibility:hidden` with layout; `measureDetailHeight` takes the max `offsetHeight`, caps to the viewport, writes `--actions-detail-min-h` = `.actions-board__split { min-height }`). The probe uses a fixed `.action-detail__source-spacer` instead of the heavy `<Card>` (cheap) and re-runs when previews land (`previewCount` watch) + on resize. `prefetchBranchPreviews` now prefetches ALL available cards (not just multi-node) so the measured heights include result chips. Result: the overlay opens at exactly the size where NO detail scrolls, fixed by the action SET, stable across selections.

**A validation reason must name ONE concrete blocker — NEVER an "X or Y" combination.** A combined reason ("No asteroid here, or you can't afford the Reds tax") forces the player to guess which applies. Split it by checking the conditions in order and returning the SPECIFIC reason (`this.resourceCount === 0 ? noAsteroid : canMaxed ? maxed : cantAffordTax`). This was the rule for the per-branch `unavailableReason` in `actionPreview` AND the card-level `actionUnavailableReason` hook. Fixed: RotatorImpacts, CometAiming, DirectedImpactors, IcyImpactors, ExtractorBalloons, TitanFloatingLaunchPad (the spend-resource→raise-param branches). NOTE: a GENUINE disjunction ("Need 1 M€ OR an asteroid" — either enables the action) keeps its "or" — that's not a guess, it's a real either/or.

**Target-card pickers (`ActionTargetCard`) wrap candidates in a per-OWNER group ONLY when targets span MORE THAN ONE player.** A single-owner pick (the common "add a resource to your OWN card" case) is rendered FLAT (`showOwners = groups.length > 1` → drop the owner header + `--flat` group frame + the amber self-border) — the player-name wrapper is pure noise when there's only ever your own cards, and dropping it reclaims modal space. Applies to BOTH the action-confirm modal and the card-play modal (both host `ActionTargetCard`). **Clicking a candidate CARD opens it FULLSCREEN** (the fork's universal "click a card → fullscreen" convention; the card click `@click.capture.stop="openZoom"` suppresses Card.vue's own zoom) — there is NO separate ⤢ button; SELECTING is the dedicated `.action-target-card__pick` button ("ВЫБРАТЬ"/"ВЫБРАНО") below the card.

**EVERY disabled button MUST carry a premium tooltip explaining WHY it's disabled** (project rule). A disabled `<button>` never fires `:hover`, so host the reason on a NON-disabled WRAPPER (`.premium-tooltip()` + `:data-hint`): the wrapper gets `:hover` from the pointer even while the button inside is disabled. Done for the details CTA (`.action-detail__cta-row` → `ctaDisabledReason`) and the modal Confirm (`.action-confirm__confirm-wrap` → `confirmDisabledReason`, which names what's still missing — payment / a selection / a branch block). Apply the same pattern to any new disabled control; a disabled button with no tooltip is a bug.

**A wrapped `<Card>` MUST suppress Card.vue's OWN click→zoom with `@click.capture.stop`.** `Card.vue` has a built-in click-to-fullscreen (`onClick` → its own `CardZoomModal`, gated on the `fullscreen_cards_on_dblclick` preference). Any clickable wrapper that ALSO opens a fullscreen (the details + modal source-card buttons → `$emit('open')` / `openFullscreen`) would otherwise fire BOTH — opening TWO viewers that each need a separate close (the "opens/closes twice" bug). `@click.capture.stop` on the wrapper intercepts the click in the capture phase and stops it before it reaches the inner `<Card>`. (The handpick card already used this pattern.)

**Source preview lives in the DETAILS panel, NOT a grid hover popover.** The old full-card hover popover over the master grid (which could cover the action rows) is GONE — `ActionDetailsPanel` instead embeds a compact, click-to-fullscreen `<Card>` source preview (`.action-detail__source-card`) under the breakdown, and the panel scrolls its own content (`max-height` + thin bar) so the CTA stays reachable. **`Card.vue` resolves its render data ONCE in `data()` from the initial card name** (NOT reactively), so a REUSED keyless `<Card>` shows the FIRST card it ever rendered — the embedded source preview MUST carry `:key="cardName"` (else switching the selected action left the source stuck on the previously-viewed card, e.g. "Метеозонды" while the panel said "Поедатели реголита"). **Availability + reasons are SERVER-authoritative** (mirrors the hand overlay). `src/server/models/actionUnavailableReasons.ts` (`actionUnavailableReasons(player, card)`) returns `[]` when `card.canAct(player)` (turn-independent), else collects structured `UnplayableReason[]` from THREE sources, in order: (a) for DECLARATIVE action cards it mirrors the action-relevant `Executor.canExecute` checks reading `card.actionBehavior` (a new `Card`/`ICard` getter — distinct from the `action()` METHOD), emitting per-failing-check reasons (spend resources → `'resource'` reason type with the resource icon, decreaseAnyProduction → `target`, placement → `placement`, addResourcesToAnyCard mustHaveCard → `target`, drawCard → `rule`, etc.); (b) — consulted only when (a) surfaced nothing — the card's own **co-located `ICard.actionUnavailableReason?(player)` hook**, a ONE-LINER in the card file right next to `canAct` (e.g. `return actionReason.notEnoughEnergy()`); (c) an honest generic fallback so the popover is never empty. **The hook lives IN THE CARD FILE on purpose** (NOT a centralized table): this is a fork that merges upstream, which owns the card files — when upstream changes a card's `canAct`, the reason is in the SAME diff/conflict, so it can't silently drift; a fork-only central table upstream never touches would merge cleanly and rot. The hook one-liners pull from a thin stable builder module `src/server/cards/actionReasons.ts` (`notEnoughEnergy` / `notEnoughTitanium` / `notEnoughMC` / `needMoreMC(player, cost)` / `noResourcesHere` / `noEnergyProduction` / `deckEmpty` / `ruleReason(msg)` / `targetReason(msg)` / `placementReason(msg)`) so the CHOICE is co-located while the wording stays consistent. **Coverage is 100% and regression-guarded:** `tests/models/actionReasonCoverage.spec.ts` iterates every in-scope action card and FAILS if any that can be unavailable has neither a declarative behavior reason nor a hook (an `always-acts` card — `canAct(){return true}` — is exempt; ~12 in scope). All ~31 bespoke-`canAct` in-scope action cards carry a hook; declarative cards with a bespoke gate (Water Splitting Plant's Reds-tax when energy is fine) carry a hook too (the behavior reason fires first when the covered check is the blocker).
