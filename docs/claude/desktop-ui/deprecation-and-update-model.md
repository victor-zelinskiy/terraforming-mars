## Update model — NO-REMOUNT + structural sharing + unified motion system (the 2026-07 rework)

**The per-response `playerkey` remount is GONE** (design + status: `docs/REMOUNT_ANIMATION_REWORK_DESIGN.md`). The game subtree (today `<ConsoleShell>`; historically `<player-home>` / `<spectator-home>`) carries no `:key` and lives for the whole game session; a server response applies the fresh `playerView` reactively. The `?remount=1` / `tm_remount` rollback ladder was RETIRED in the desktop-removal cleanup (2026-08-23) — `legacyRemount.ts` is deleted and nothing keys on `playerkey` in any mode. Everything below follows from that:

- **`playerkey` is now the transient-UI RESET EPOCH, not a `:key`.** All 5 historical bump sites (App.update commit, `WaitingFor.updatePlayerView`, DraftFlow / InitialDraft / StartGameFlow overlays) still bump it behind the SAME preserve guards (`preserveCardPickModal` / `preserveOpenOverlay` / draft-preserve / sale-preserve); PlayerHome receives it as the `:reset-epoch` prop and its watcher runs **`resetTransientUi()`** — the explicit replacement for the implicit data()-reset the remount used to perform (closes `activeOverlay`+pending modals/confirms/pickers, then re-arms exactly what a fresh mount would have re-armed: mandatory-prompt overlays by module-state `minimized` flags, then actions/hydro via `epochResetTargetOverlay()`, applied as ONE overlay transition — never an open→null→open flap, so genuine-close side effects like `resetHydroPlan` don't fire for an overlay that merely survives the reset). When you add NEW transient PlayerHome state that a submit must clear, reset it in `resetTransientUi()` — do NOT assume a remount will clear it.
- **Structural sharing (`src/client/utils/viewSnapshotShare.ts`).** Every commit path assigns `nextViewSnapshot(prev, incoming)`: a tree CONTENT-IDENTICAL to the fresh snapshot in which every deep-equal branch keeps the PREVIOUS reference. The ROOT identity always changes (so identity-watchers on `playerView` — App / NotificationLayer / TurnHandoffLayer / StartGameFlow — keep firing), while unchanged children (board spaces, players, cards) keep their refs → their components skip re-rendering. It never mutates either tree; the worst bug class is a wasted re-render, never wrong data. Deliberately chosen over an in-place reactive merge (which silently kills identity-watchers + needs delete/replace handling).
- **The two rules the remount used to cover:**
  1. `Card.vue` resolves `cardInstance` in a **computed** now — a keyless re-pointed `<Card>` re-resolves its render data correctly. The `:key="cardName"` advice for re-pointing hosts still applies for internal state, but render-data staleness is structurally fixed.
  2. Anything that used `mounted()` to re-derive per-response state must use a **value-based watcher** instead (`WaitingFor`'s title/favicon/spinner ride a `waitingfor` watcher — `syncTurnPresentation()`; PlayerHome invalidates the board-info fact caches via `playerView.game.gameAge`/`undoCount` watchers). NEVER add an identity-watcher expecting per-response firing on a SUB-object of playerView — shared branches keep identity; watch VALUES (gameAge / undoCount / the concrete field).
- **Unified motion system (`src/client/components/motion/motionTokens.ts`).** ONE source of truth for animation speed: JS timings resolve through `motionMs(base)`, CSS animations through `calc(<base>ms * var(--motion-scale, 1))` (`--motion-scale` set on `<html>` at bootstrap in `main.ts`), so the whole choreography scales in lockstep. Speed presets `calm | standard | swift` (×1.3 / 1 / 0.65; `standard` = the shipped timings byte-identical): `?motion=<preset>` / `localStorage tm_motion_speed`. FPS cap for rAF-driven loops (`createFrameGate`; ares glide, energy-conversion / hazard-cleanup interpolation): `?motionFps=30|60|auto` / `tm_motion_fps` (CSS/WAAPI animations are compositor-driven and not affected — documented limitation). Easing tokens `MOTION_EASE` for new work; `prefers-reduced-motion` stays a separate overriding axis. Wired through: delta-chip lifetimes + merge window, WGT marker hold, tile-placement hold/duration (flows into CSS via the inline `--placement-duration`), energy→heat, hazard cleanup, scale-marker glide+settle. **When adding a new animation: take the duration through `motionMs()` (JS) or `calc(...*var(--motion-scale,1))` (CSS) and reuse `MOTION_EASE`** — don't hand-roll fixed durations. A premium in-game preset switcher UI is a follow-up (no premium settings surface exists yet).
- **`AnimatedMetricValue` fires chips ONLY from watch-transitions (honest old→new).** A genuine mount is a SILENT baseline (`changeFeedbackManager` keeps the scope semantics: real update → chip; seat switch → suppressed re-baseline; initial load → baseline). The historical mount-diff branch rode the remount flag and was deleted with it.
- **Rollback (client-side, instant):** `?patch=0` / `tm_patch=0` → wholesale swap instead of structural sharing. The second rung — `?remount=1` / `tm_remount=1` full legacy keyed remount — was RETIRED 2026-08-23 (it only ever keyed the deleted `<player-home>`). The animation baseline modules (`accentBaseline`, `tileBaseline`+resume, cube baseline) STAY: the live board diffing / hydration paths still read them (first-sight baselines, F5, `v-show` display round trips).
- **Per-subsystem comments saying "survives the playerkey remount"** describe why state is module-level; the historical wording survives in many files, and the placement rationale still holds (App-level mounting + the reload game boundary are unchanged). The per-game module singletons were deliberately NOT migrated back into components.
- **Guards' meaning shifted, not their logic:** where a guard used to mean "skip the remount" it now means "skip the transient-UI reset". Same predicates, same call sites.
- Perf counters for before/after (`?perf=1`): `playerHome:mount` (once per session now vs once per response), `metricValue:mount`, `playerHome:resetTransientUi`, plus the existing `playerView:commit` + long-task observer.
