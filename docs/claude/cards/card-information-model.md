## Card Information Model (structured per-graphic-block card text)

**Every in-scope card (457: project + prelude of base/corpera/promo/venus/colonies/prelude/ares) carries `metadata.information` — structured text blocks, one per self-contained graphic block** (`src/common/cards/CardInformation.ts`: groups `requirements → immediate → effect/action → victory-points`, blocks `{id, kind, text, graphicId}`). This is the DATA FOUNDATION for the future fullscreen right-hand info panel; the panel itself is NOT built. The monolithic `metadata.description` is LEGACY (legacy renderer only — never consume in new code).

- **LOCALIZATION PRINCIPLE (load-bearing): every text in code is ENGLISH ONLY — the text IS the i18n key.** Translations live exclusively in the locale jsons (`src/locales/<lang>/card_info.json` for generated/authored keys — a HAND-MAINTAINED file, the generator never writes it; DSL strings are already in `<lang>/cards.json`). The generator only VALIDATES coverage for `ENFORCED_LOCALES` (ru today) and reports gaps in the audit's `missingTranslations` — adding German/Ukrainian later = fill the same keys in a new json, zero code changes.
- **GENERATED at build time** (`make:cards` → `src/server/tools/cardInfo/buildCardInformation.ts`, chained in `export_card_rendering.ts`) from the CANONICAL sources — NO runtime prose parsing: requirements ← descriptors (baked-number template texts; the `cities{nextTo}`+`oceans` PAIR merges into ONE composite block); immediate ← the executable `behavior` (numbers baked in — generated text can never lie; a `behavior.tile.adjacencyBonus` rides its tile line as «…that grants an adjacency bonus of N <res>» — `adjacencyBonusText`); effects/actions ← the DSL nodes' co-located descriptions (keys keep the `Effect:`/`Action:` prefix — the client strips it for display, established pattern); VP ← a `victory-points` infoText entry, else the `vpText` node (TINY+uppercase TEXT item), else the `{resourcesHere,per}` template. Plain numeric VP / cost / tags / expansion / live counters produce NO blocks (self-explanatory metadata).
- **⚠️ THE GENERATOR MUST NOT DROP A `behavior` SUB-FIELD (the "lost rule" class — guard-enforced).** A tile placement bakes its KEY RESTRICTION and every qualifier onto the line — the generic «Place an X tile.» silently dropping them broke production (Artificial Lake lost «ON AN AREA NOT RESERVED FOR OCEAN»). Handled: `ocean.on`/`city.on`/`greenery.on`/`tile.on` → a placement clause (`placementClause` + `PLACEMENT_CLAUSE`: land→«not reserved for ocean», ocean→«reserved for ocean», volcanic, isolated→«not next to any other tile», away-from-cities, upgradeable-ocean→«on top of an existing ocean tile»; `DEFAULT_PLACEMENT` skips the NORMAL placement per tile kind — a special tile on `land`/`city` gets no clause); `ocean.count:2`; `city.space` → «on the reserved area» (off-Mars slots); `colonies.buildColony.allowDuplicates` → «even where you already have a colony»; `adjacencyBonus.cost` → «Other players pay N M€ more…» (Nuclear Zone). A rule the generator CAN'T derive (a composite «counts as a city AND an ocean» — Ocean City / New Holland; «disregarding normal placement restrictions» — Mangrove) → co-located `infoText`. **The guard `behavior-derived cards do not drop any KEY rule` word-diffs every `ok`-status card's generated text vs its description (synonym-folded) and FAILS on any uncovered content word** — a genuinely-fine residual (a rule carried by a printed TAG / board geography / only-wording-differs) goes in the test's `ACCEPTED` map with a reason, never silently.
- **⚠️ ORDER IS THE ONLY CARRIER OF SEQUENCE (HARD REQUIREMENT, guard-enforced).** The player reads the on-play sequence TOP-TO-BOTTOM, so: (1) **a block NEVER uses a sequencing connective word** («then», «afterwards», «finally», «subsequently», «firstly/secondly/…») — convey order by BLOCK ORDER instead (banned list guard; NOT «next»/«after»/«before»/ordinals, which are legit rule wording); (2) **block order MUST follow the card's RENDER reading order** (row-by-row, top-to-bottom), which is itself authored to match the real on-play EXECUTION order. Behavior-derived immediate blocks are auto-sorted to render position by **`orderBehaviorBlocks`** (the `behaviorBlocks` emission order is a FIXED key order — spend→production→stock→…→tile — that can disagree with the render; this sort reconciles it). AUTHORED `infoText` is NOT auto-sorted (the author controls order, incl. no-graphic step blocks) — the guard catches a mis-ordered infoText, fix by reordering the array to render order. If a card's render itself is out of execution order, fix the RENDER (a card-authoring bug), not the info model.
- **`hasBespokePlay` detects an override ANYWHERE in the prototype chain** (`card.bespokePlay !== Card.prototype.bespokePlay`) — an own-prototype `hasOwnProperty` check MISSED an Ares/promo subclass that INHERITS its parent's bespoke tile placement (GreatDamAres → GreatDamPromo), so the card looked fully declarative and its bespoke tile + adjacency silently vanished (status `ok` instead of needs-curation). A subclass with a partial `behavior` + inherited `bespokePlay` needs co-located `infoText`.
- **Bespoke texts are CO-LOCATED in the card files: `metadata.infoText`** (`CardInfoText[]` — `{kind?, text, tokens?}`, EN keys only; `tokens` link to graphic rows). 71 cards authored. This follows the fork's co-location convention (an upstream card change surfaces in the same diff); there is NO central fork-only registry. `infoText` is generator INPUT — stripped from the exported client metadata (`information` is the output). Cards whose `metadata` rides a CONSTRUCTOR PARAMETER default (MiningRights/MiningArea/GreatDamPromo) need the param annotated `: CardMetadata` or subclass metadata breaks type inference.
- **Graphic linkage = `deriveGraphicIds`** (`src/common/cards/render/cardGraphicIds.ts`) — ONE pure content-derived row-id function shared by the generator AND the client (`mechanicsModel` stamps `MechGroup.graphicId`); reserved id spaces: `req:<type>[:qual]` (requirements bar), `vp` (the badge), and **`tags`** (the tag cluster — for a rule ABOUT the printed tags that has no mechanic row: Research Coordination's wild-tag rule is a `note`/«ОСОБОЕ ПРАВИЛО» with `tokens:['tags']` → anchors to the wild medallion, not an isolated «ПРИ РОЗЫГРЫШЕ»). The fullscreen layer resolves them in `CardAnnotationsLayer.rowEl` (`.pcard__reqs`/`.pcard__vp`/`.pcard__tags`). Never positional. A `note`-kind block renders as «ОСОБОЕ ПРАВИЛО» (`LABEL_BY_KIND`).
- **The audit `src/genfiles/cardInfoAudit.json` is the WORKLIST**: a new bespoke card lands in `needsCuration` until its file gets `infoText`; new untranslated keys land in `missingTranslations.<lang>`; `seeded` = single-block cards riding their printed description; **`seededRunOn`** = seeded cards whose single block is a MULTI-SENTENCE run-on paragraph (the design wants one line per bonus) → split them into ordered `infoText` blocks.
- **vpText leaves the premium face**: `buildMechanics(..., {dropVpText})` (set by the VM only for DYNAMIC-VP cards) drops the TINY-uppercase fine print — the rule lives in the VP block; the badge formula stays.
- **A `vpText` node must carry ONLY the VP rule** — some authors cram a non-VP rule into it (Ecological Zone:ares bundled «The tile grants an adjacency bonus of 1 animal» in with «1 VP per 2 animals»), and the generator dumps the whole string into the VP block. Fix with co-located `infoText`: an `immediate`/`effect` block for the non-VP part + a `{kind: 'victory-points'}` entry (sets `vpTextOverride`, replacing `findVpText`) for the clean VP line. Guard-enforced.
- **A block ABOUT the card's own tile must TETHER to it (never a floating note).** New Holland's «The tile counts as a city and an ocean» rode as an unlinked `note` (pointed at nothing) — a property of the placed tile belongs `immediate` + `tokens:['tile-']`. The unlinked-block audit now includes notes (excluding them hid this class), and the guard fails on any block whose text talks about `this tile`/`the tile counts|grants|provides`/`counts as a city|ocean|greenery` without a graphicId. A graphic-less clarification about something ELSE (Astra Mechanica «may not be cards that place special tiles», Established Methods fallback) is fine.
- **Guards:** `tests/cards/cardInformation.spec.ts` (18) — full coverage (pinned honest-empty: Trans-Neptune Probe), unique ids, ru for every text, requirement separation + no prose leaks, no in-card duplicates, graphicId resolution against the shared derivation, the Asteroid 3-block flagship, group order, out-of-scope carries nothing, **NO sequencing connective words**, **immediate blocks in RENDER READING ORDER (row-monotone)**, **NO KEY rule dropped from the description** (the word-diff loss guard + its `ACCEPTED` map), **the VP block carries ONLY the VP rule**, **a tile-property block tethers to the tile**. **To extend scope:** widen `SCOPE_MODULES` in the generator + spec, run `make:cards`, author `infoText` for what the audit lists (incl. `seededRunOn`), translate `missingTranslations`, and clear the loss guard (add a generator field for a dropped `behavior` qualifier, or `infoText` for a bespoke rule).
