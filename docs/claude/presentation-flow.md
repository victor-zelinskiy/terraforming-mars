## Presentation Flow — the ONE foreground timeline (notifications / theater / journal / modal queue)

**The client presents ONE blocking foreground item at a time; everything else waits in a FIFO queue.** The server stays authoritative (it may already know the next prompts) — this layer only sequences CLIENT-SIDE delivery so a result modal, a mandatory choice, the MarsBot theater and the notification feed never overlap. It is NOT a z-index fix: the orchestrator is `src/client/components/presentation/` — `presentationPolicy.ts` (the PURE vocabulary + decisions, unit-tested: item kinds `mandatory-choice`/`result-modal`/`turn-theater`/`turn-event-notification`/`passive-toast`, `foregroundBlockReason` priority result-modal › theater › mandatory › ceremony, `pendingQueueSummary`) and `presentationFlow.ts` (the reactive singleton). Occupancy comes from THREE source kinds: **derived module states** (imported leaf modules: `hasPresentableReveal(parkSupplier)` [drawn-cards result modal — only batches that will actually PRESENT; see the REVEAL PARK EXEMPTION below], `revealViewerState.open` [the read-only revealed-cards viewer; the legacy `revealResultState` module is DELETED — nothing raised it since the desktop overlay waves], `marsBotTheaterState.active||lingering`), **leases** (`acquireForegroundLease('mandatory-choice')` held by MandatoryInputModal [only while `!minimized && !suppressed && !pickerMode`], DraftFlowOverlay [`shouldShow`], StartGameFlowOverlay [`showFull`], ConsoleShell [`consoleMandatoryPresenting` = task host / start scene / gov-support / reveal overlays, non-deferred]; release fns are idempotent, watchers keep them in lockstep with EFFECTIVE visibility), and an **injected flow-hold supplier** (`registerFlowHoldSupplier` — notificationState reports a visible `holdsFlow` card; injection keeps the graph acyclic: presentationFlow NEVER imports notificationState). Predicates: `isNotificationDeliveryBlocked()` (any blocking foreground) and `isMandatoryPromptsHeld()` (theater open OR a visible flow-holding card — NEVER ordinary toasts). Transitions broadcast via a module-level watch → `onForegroundFreed` (notificationState drains the queue) / `onForegroundBlocked` (visible transient cards are RE-QUEUED to the front — nothing floats over a modal, nothing is lost); `NotificationLayer.update()` also calls `promoteFromQueue()` as the self-heal for a blocker that opened+closed within one tick (invisible to the watch).

- **Serial notifications:** `MAX_VISIBLE_TRANSIENT = 1` — one card at a time, FIFO (priority-first within the queue; a hostile loss still EVICTS a visible normal card). `pushTransient` while blocked → queue, never on top. The **pending indicator**: desktop — the clickable `.notif-pending` pill under the feed («+N · События в очереди», amber accent when the queue holds critical items; click → opens the journal, and the `journalOpen` watcher runs `drainQueueToJournal()` — ordinary queued cards are dropped [the journal shows them all], `negative` + `holdsFlow` cards are KEPT); console — the informational `.con-banner--events` chip in the banner band (below the deferred chip).
- **MarsBot turns are NOTIFICATION-FIRST with STAGED VISUAL COMMITS.** Both commit paths (`App.update` poll + `WaitingFor.fetchPlayerInput`) call `presentFreshBotTurns(prev, next, {commitLatest})` (`marsbot/marsBotPresentation.ts`); when the response carries fresh bot turns it returns TRUE and the caller must NOT commit — the latest view is BUFFERED (`marsBotStagedCommits.ts`), the presented view's stale `waitingFor` is cleared (no acting on a stale runId), and the presented state advances turn-by-turn: when turn N's compact card is DELIVERED (the module `watch` on the visible bot card — pre-flush, mutation lands before paint), `deliverBotTurnVisual` applies THAT turn's footprint to the presented view (tiles via the armed placement animation + global params + per-player resources/production/TR — in-place mutations, absolute `after` values ⇒ idempotent, same pattern as the WGT/tile previews); the LAST pending turn's delivery runs the buffered full authoritative commit instead (its changes + everything newer, incl. a mandatory prompt — which the server can only raise AFTER the batch, since a prompt stops the game loop). Consequences never precede their explanation; after the drain presented ≡ latest. The per-turn footprint is SERVER-authored: `MarsBotTurn.visual` (`AutomaTurnLog` board snapshot-diff: `tiles[{spaceId,tileType,color}]` + before/after `temperature/oxygenLevel/oceans/venusScaleLevel`); resources ride the existing attack/impact steps. A response with NO fresh turns while a window is open only refreshes the buffered latest (never commits under the sequence); with no window it commits immediately (human actions are never delayed). Self-heals: notifications disabled → immediate commit at stage time; pending cards vanished from the presentation → `ensureBotPresentationLiveness()` in `NotificationLayer.update()` commits. The marker/tile/conversion holds are SKIPPED on a staged response (bot tiles animate per turn; a transient conversion marker is picked up by the next poll — the documented poll-path behaviour). `resetBotStaging()` on the game-switch boundary. Each fresh turn is archived (`marsBotTurnArchive.ts`, reactive Map keyed `${botColor}:${gen}:${id}`, fed by `automa.lastTurn` + the new bounded `automa.turnHistory` tail — consecutive bot turns inside ONE human input are no longer lost; a fresh session seeds SILENTLY) and enqueued as a compact card: variant `bot-turn`, kind important, priority 2, **TTL 5s**, headline = the turn's own reveal/pass log line, CTA «Осмотреть» (`expand-theater`) + ghost «В журнал». **The compact card CARRIES the turn's outcome** (a player who never expands still understands what happened): `NotificationModel.summaryLines` = the turn's own key LOG lines (placements / parameter raises / losses / failed-action money; SPACE tokens keep «показать»; capped at `BOT_TURN_SUMMARY_CAP`=3 with an honest `summaryOverflow` "+N" marker) and the pills LEAD with global-parameter before→after chips (`globalParamChips(prev,next)` — `JournalImpactChip.neutral: true`, never sign-tinted; attached only when exactly ONE fresh turn rides the response) followed by the viewer-first resource impacts. Internal automa bookkeeping (tag processing, track advances) is deliberately NOT on the card — inspect-only. **The card `holdsFlow: true`** — while it is VISIBLE, mandatory surfaces (draft modal / mandatory input modal / console task surfaces) hold off mounting (bounded by the TTL — the game can never stall). The player ACTING auto-acknowledges it (`acknowledgeFlowHoldingCards()` at the top of `fetchPlayerInput`). «Осмотреть» → `openMarsBotReplay` runs the theater as a self-contained REPLAY (`runMarsBotTheaterReplay`; the theater flips active BEFORE the card is dismissed so the next queued card can't sneak under it); while open (playing OR lingering) it blocks delivery + holds mandatory surfaces; `isMarsBotTheaterActive()` still guards poll re-commits. **The theater is a turn REVIEW, not a live-turn simulation:** the synthetic `thinking` intro step is DELETED from the model (`TheaterStep` has no 'thinking' kind), the headers read «подробности хода» (`'turn details'` / lingering `'turn complete'`, aria `'AI turn details'`), and the old «Поле обновлено — закройте, когда дочитаете» footer is GONE (the board updates WITH the notification; the inspect applies nothing). The console bot-turn card shows its own pad contract ON the card (`.con-notif__actions`: «зажать X Осмотреть ход» · «B Закрыть» — NOT echoed by the command bar, which keeps the current screen's contract; EVERY console toast carries the «B Закрыть» chip). **Presentation-mode knob** (architecture for a future setting, mirrors motionTokens): `?botTheater=1` / `tm_bot_presentation` / `setMarsBotPresentationMode` (URL → in-session override → localStorage) → `'theater'` auto-expands the card into the theater the moment it is DELIVERED — even auto-theater rides every gate/queue.
- **Journal = the permanent memory of the same script — STRICTLY one entry per bot turn.** The whole bot turn resolves inside ONE `events.beginAction(bot, undefined, {category: 'automa-turn'})` scope (`AutomaController` — the scope CLOSES before `playerIsFinishedTakingActions`, which can start the next turn synchronously); its `correlationId` is stamped onto `MarsBotTurn.correlationId` (`AutomaTurnLog.finish`), so notification, theater and journal share ONE key. **AUTOMA-TURN COALESCING (`EventRecorder.beginAction`):** ANY nested `beginAction` opened while an 'automa-turn' scope is on the stack (the Delta advance, a milestone claim, an award funding — incl. shared human/bot code paths like `Game.fundAward`) JOINS the turn's chain instead of rooting its own journal group — its 'action' event keeps its own `category` (analytics / endgame facts unchanged) but carries the TURN's correlationId, and its scope stamps logs as `detail` (never a second root-action that would split the entry). **`buildJournalView` never collapses a single-line 'automa-turn' group to a flat row** (the group shape carries the accent + the replay affordance — a bare-reveal turn must still offer X). The journal groups the turn (`.journal-group--automa-turn` accent); a group with an archived script renders the «Осмотреть ход» pill (desktop `JournalGroup`) / serves X = replay (console `ConsoleJournalPanel`, which closes the journal so the theater band owns the pad). Replay is read-only — never a game event, never a server round-trip. `diffRootNotifications`' output is filtered by `category !== 'automa-turn'` in the layer (the dedicated pipeline builds the richer card — no double-announce; a coalesced nested Delta/milestone shares the turn's correlationId, so it can't leak a second card either). Known non-turn exception: the automa END-GAME final greeneries happen outside `takeTurn` (no scope, no script) — flat lines by design.
- **WaitingFor's modal routing during a hold:** a modal-routed prompt renders NOTHING while `presentationHeld` (neither the modal nor the inline factory — the empty `v-else-if` branch); console keeps its byte-identical `modalSuppressed` fallback. The console's holding card / theater band are registered leak-detector serving surfaces (`.con-notif--holding`, `.con-bot-theater`) so a held prompt is never "stranded". Console input while a toast is up: the command bar KEEPS the current screen's contract (a toast never re-labels it) and the card carries its own hints (`.con-notif__actions` — «B Закрыть» on EVERY toast; the holding card adds «зажать X Осмотреть ход»). The toast overrides exactly two edges: B closes it, and the DETAIL action fires on press-and-HOLD X (`consoleNotifHold.ts`, fixed `NOTIF_HOLD_MS` = 500; the card's fill plate takes the SAME constant inline so visual and timer can't drift; the TTL shrink pauses while the fill runs). A single X TAP is captured on press and REPLAYED through `handleIntent` on the release edge (guarded by `notifTapReplay`), so the console-wide inspect verb beneath is never stolen; A / navigation pass through untouched (a deliberate acting press auto-acknowledges the holding card via `acknowledgeFlowHoldingCards`). The release edge of a tracked hold is resolved at the TOP of `handleIntent` — ahead of every swallowing gate — and `consoleKeyBridge` synthesizes `release` intents from keyup so the hold works on keyboard too.
- **Result modals use snapshot payloads** (verified: drawn-cards reveal renders the server's `cardDrawReveals` batch, the reveal-result overlay renders `lastReveal` — never live state).
- **ANIMATION HOLDS — every CRITICAL premium animation is a first-class foreground occupant (`src/client/components/presentation/animationHold.ts`).** The per-flow `holdingFor*` gates only held the COMMIT; the post-commit halves (reveal/reward beats, ceremonies) and the poll-driven notification feed could still be covered by a new modal/toast. The registry is the ONE contract: while ≥1 hold is live, `foregroundBlockReason() === 'animation'` (notifications queue — nothing floats over a scene) and, for `'blocking'`-scope holds, `isMandatoryPromptsHeld()` (the mandatory modal / draft / console task host wait); the LAST release fires the existing freed-broadcast → the queue drains at once. **The release IS the flow's own completion signal (GSAP onComplete → the flow's reactive flag drops) — NEVER a timer**; a 35 s ceiling (deliberately ABOVE every per-flow safety, so the flow's abort always cleans up first) force-releases a leaked hold with a warn. Two attachment styles: (a) `registerAnimationHoldSupplier(label, predicate)` at module scope for flows with a reactive "scene owns the foreground" predicate — registered: played-hero, patent-sale, tile-placement, trade-fleet, hydro-marker, resource-transfer, energy-conversion, hazard-cleanup, gov-scale-focus, ma-ceremony-own (the viewer's OWN coronation only — the remote beat is unobtrusive by design), deck-draw + board-card-bonus (both `scope: 'notification-only'`); (b) `beginAnimationHold(label)` handle (idempotent release from every exit path) for component beats — the card-deal sequence (released in its `finish()` funnel, `'notification-only'`) and `ConsoleTerraformingCeremony`. Wrappers: `holdAnimationWhile(label, promise)` (releases on settle) and `holdForGsapAnimation(label, tl)` (releases on `.then()` completion AND on kill via a CHAINED `onInterrupt`). **`'notification-only'` is for a cinematic that runs INSIDE a mandatory surface** (the deal plays inside the task host / start scene — a blocking hold would unmount its own stage: a self-deadlock); everything else defaults to `'blocking'`. **When a new hold hides the console task host while the server waits, its DOM root must join the leak detector's `SERVING_SURFACES`** (`.con-macere` / `.con-terracere` were added for the ceremonies). `whenAnimationsSettled()` is the imperative await for future call sites.

Deliberately animation-only — a result modal / mandatory choice / theater means a human is looking at something and may legitimately take minutes. The watchdog calls `promoteFromQueue()` every pass, in every scope, so the deadline always has a clock.

- **ROUND 4 (2026-08-04) — THE ACTUAL ROOT CAUSE: a non-reactive supplier predicate.** The decisive log line was `[notifications] 1 queued event(s) held behind an ANIMATION hold … (leaked hold: none named)` — `foregroundBlockReason()` said `'animation'` while `activeAnimationHoldLabels()` (an uncached, direct read) listed NOTHING. - **⚠️ A PROMISE AROUND A GSAP ANIMATION MUST SETTLE ON `onInterrupt`, NEVER ONLY ON `onComplete`.** GSAP fires `onComplete` only for a natural finish — a killed tween (element unmounted, `killTweensOf`, an overwrite, a teardown mid-flight) never calls it, so `await tween(...)` hangs FOREVER, the enclosing `try/finally` never runs, and whatever it was going to undo leaks permanently. In `handDeliveryDirector` that is `activeRuns`, which pins the `'notification-only'` `hand-delivery` supplier true for the whole session — exactly the freeze shape above (`flights.length` is already 0, so `cardArrival` stays false and only `anyAnimation` shows). - **PROMPT IDENTITY IS NEVER THE RAW TITLE — `promptIdentityKey(wf)` (`turnIntents.ts`).** `translateMessage` rewrites `Message.message` IN PLACE on first render, so a `type|title` key silently flips from the English template to the localized one part-way through a prompt's life. The key normalizes the title through `translateText`, which is idempotent over the mutation (English key → localized; already-localized → unchanged) and keeps exactly the old discrimination. This is invariant #1 applied to prompt IDENTITY, not just detection.
