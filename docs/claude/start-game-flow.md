## Start-of-game flow — unified premium orchestration modal (`StartGameFlowOverlay`)

The whole start of generation 1 (play your 2 preludes one-by-one → apply the corporation's mandatory first action → confirm "begin the game") is driven by ONE App-level premium modal: `src/client/components/startGameFlow/StartGameFlowOverlay.vue`. It REPLACES, for the start sequence, both the bare prelude card-selection (`'Select prelude card to play'`, formerly `DraftFlowOverlay → CardSelectionContent`) and the corp first-action `OrOptions` (`'Take first action of X corporation'`, formerly `MandatoryInputModal → ModernOptionPicker`). Ordinary action modals stay focused — there is NO source-card / hero context injected into them (an earlier `StartEffectHeader` / `source`-threading experiment was fully rolled back, client AND server).

**Why App-level + module-state** (same rationale as `DraftFlowOverlay` / journal): `App.vue` mounts `<player-home :key="playerkey">` and bumps `playerkey` on every server response, remounting that subtree. The overlay is mounted as a SIBLING of `<player-home>` (in `App.vue`, next to `DraftFlowOverlay`, `:player-view` + `:waiting-on-players`), so it survives the remount and keeps the flow continuous across prelude → sub-action → waiting-for-others → corp → first turn. Its visibility latches sticky (see `startGameFlowActive`).

**Single source of truth = `src/client/components/startGameFlow/startGameFlowState.ts`** — owns the reactive `startGameFlowState` AND every predicate, so the overlay and the two legacy-suppression sites import ONE implementation. **State is keyed PER-PLAYER, not global:** `activatedPlayers` / `completedPlayers` are arrays of `view.id`, NOT single booleans. The module is shared across every player viewed in the SAME client (hot-seat / player switch), so a global `completed=true` (player 1 pressing "begin the game") would unmount/disable player 2's still-pending flow AND let the legacy corp `OrOptions` modal leak back in. `startGameFlowActive(view)` therefore checks `completedPlayers.includes(view.id)` / `activatedPlayers.includes(view.id)` — derived in the predicate (no watcher-reset race). `markStartFlowActivated(id)` / `markStartFlowCompleted(id)` mutate the arrays; `minimized` stays a single transient value (always reflects the currently-viewed player, re-derived by the overlay watcher each view change). The predicates:
**Detection is via an EXPLICIT server marker, never the (translatable) title** — see the i18n gotcha below for why. `BaseInputModel.startGamePrompt?: {kind: 'corporationInitialAction' | 'corporationSelection' | 'preludeSelection', preludeMode?: 'hand' | 'draw' | 'copy'}` (server: `BasePlayerInput.markStartGamePrompt(meta)`, set on the corp OrOptions in `Player.ts`, the SelectCard in `PreludesExpansion.selectPreludeToPlay`, and Merger's corp-select SelectCard in `Merger.bespokePlay`; serialized centrally in `ServerModel.getWaitingFor` next to `warning` / `pendingInitialActions`). The predicates:
- `startFlowPreludePrompt` / `startFlowPreludeDrawPrompt` / `startFlowPreludeCopyPrompt` — a `preludeSelection` SelectCard of mode `'hand'` (the player's own starting preludes → the grid) / `'draw'` (drew N, choose ONE, discard the rest — New Partner / Valley Trust → the draw-choice block) / `'copy'` (pick one ALREADY-PLAYED prelude to copy — Double Down → the copy block). `preludeMode` is computed authoritatively server-side: `'copy'` iff `cardAction === 'double-down'` (the ONLY reliable signal — Double Down's candidates are played preludes but can include New Partner from the hand, so a cards-vs-hand check misclassifies it), else `'hand'` iff `cards.every(c => preludeCardsInHand.includes(c))`, else `'draw'`. `startFlowAnyPreludePrompt` = any of the three.
- `startFlowCorpPrompt(view)` — an `OrOptions` whose `startGamePrompt.kind === 'corporationInitialAction'`. `corpActionOptionIndex(prompt)` returns the option without the `'pass'` warning (single-corp). For the MULTI-corp case (Merger gives a 2nd corp), `corpActionOptionIndexFor(prompt, corpName)` matches the option by its CARD token (the corp name, translation-proof) so each corp gets its own ПРИМЕНИТЬ ЭФФЕКТ. `corporationCardNames(view)` = all `CardType.CORPORATION` tableau cards (base + merged) in order; `corpStatusFor(view, name)` = `ready` (live OrOptions has an option for it) / `pending` / `done`. The corp area renders one COLUMN per corp with the apply button UNDER the card (so a second corp has room to its right).
- `startFlowCorpSelectPrompt(view)` — Merger's `corporationSelection` SelectCard (choose ONE of the dealt corps; unaffordable ones arrive with `CardModel.isDisabled` and render as a disabled "Недостаточно M€" hint). Picking submits `{type:'card', cards:[name]}`; the chosen corp joins the tableau (`playCorporationCard` → it shows in the corp area, and if it owes an initial action that flows through the corp OrOptions); the 42 M€ payment is a normal `SelectPaymentDeferred` sub-action. Suppressed in `DraftFlowOverlay` alongside the prelude prompts, and folded into `eligible` / `allDone` / `hasFocusedSubAction`.
- `preludeEntries(view)` — the player's STARTING prelude set for the grid, in a **STABLE order** (`preludeOrderStore`, a per-player append-only Map): a prelude's slot is fixed the first time it appears and NEVER reorders, so playing it only flips its status in place — it does NOT jump to the front (the grid `:key="entry.name"` keeps the element identity). played = `thisPlayer.tableau` filtered by `getCard(name)?.type === CardType.PRELUDE`; awaiting = `preludeCardsInHand`. ONLY drew-N-choose-ONE ('draw') candidates are EXCLUDED (`drawChoiceCandidateNames`, recorded at pick time) — they live in their own block. Double Down ('copy') candidates are NOT recorded and NOT excluded: they're already-played preludes that must STAY in the grid (the bug fixed here was treating a copy-source pick as a 'draw' choice, which deleted the source from the grid and broke the prelude counter). `playByName` dispatches a pick: draw → `playDrawPrelude` (records), copy → `playCopyPrelude` (submits, no record), else `playPrelude`. The order store is NON-reactive (it's written inside the `preludeEntries` computed; a reactive write would re-trigger it) and cleared on reset / completion. **Fizzle-warning (NOT a block):** a playable prelude the server flagged `preludeFizzle` (it would do nothing now — Double Down before any other prelude is played, nothing to copy; Eccentric Sponsor with no affordable card in hand) gets `fizzles: true`. It stays **fully playable everywhere** — grid button, `playableZoomNames`, console focus rail — because the tabletop puts no order restriction on preludes: burning one for `PreludesExpansion.fizzle`'s 15 M€ is a legal (bad) play, and an earlier iteration that withheld РАЗЫГРАТЬ removed that choice from the player. Upstream carries the same intent as a `TODO(kberg)` on `EccentricSponsor`: identify the fizzle during `canPlay` "which will present a **warning** to the player" — the fork implements it (the `canPlay` override running the real `getPlayableCards({extraDiscount: 25})`), and stops at a warning.

The COPY is `preludeFizzleNotice(entries, name)` — ONE pure decision returning the i18n key for both surfaces (the branch used to be hand-copied in each, which is the shape that drifts). It asks: is another non-fizzling playable prelude still in hand? Yes → «Сначала разыграйте другой пролог» (actionable: playing that one first may well make this one live). No → the canonical warning copy «Этот пролог сейчас не сработает — вы сбросите его и получите 15 M€.» (the shared `cardWarnings.ts` `preludeFizzle` key), because with nothing else live the advice would point at nothing. Console renders it as an amber `con-cards__pickband--warn` badge on the card (at-a-glance, survives losing focus) plus the sentence in the ceremony status rail; desktop renders `start-game-flow__fizzle-note` ABOVE a live РАЗЫГРАТЬ.

**THE ORDER-AWARE GATE (server verdict + console risk stage).** `preludeFizzle` answers ONE bit — «not now» — and one bit cannot tell «Удвоение played FIRST has nothing to copy YET» from «this can no longer work». The UI that rendered one bit therefore printed «Сначала разыграйте другой пролог» beside a command bar reading «A — Подтвердить»: two true sentences whose only joint reading is «press A to go to the other prelude», and A discarded the card. The fix is structural — one **server-computed verdict** that the warning, the badge, the stage AND the button label are all derived from.

**The verdict** (`common/cards/PreludeOutlook.ts`, computed by `server/preludes/preludeOutlook.ts`, shipped on `CardModel.preludeOutlook`, mirrored to `PreludeEntry.outlook`): `playable` · `deferred {certainty: 'guaranteed' | 'possible', enablers, need}` · `noEffect`. Three rules keep it honest. **① NO SIMULATION** — it reads the card's own `canPlay` (the real rule source) and each candidate enabler's DECLARED behaviour, never a counterfactual game state; a future it cannot read is a POSSIBILITY, never a guarantee. **② NO CARD NAMES** — an order-dependent prelude says so itself, in its own file, with one word (`preludeNeeds: 'playedPrelude' | 'playableCard'`, co-located beside its `canPlay` per the fork's co-location law); the engine knows only those two vocabularies, and derives what a card PROVIDES from `behavior` (`drawCard` / an M€ gain) plus the `preludeProvides` escape hatch. **③ SERVER-AUTHORITATIVE** — there is no second client-side rules engine to disagree. `certainty` is a property of the NEED: creating a played prelude is what playing one IS (`guaranteed`); «this may put a playable project in your hand» is a hope about unseen cards (`possible`). The `pool` is the player's REMAINING preludes in hand, never the candidate set — in a drew-N ask the rivals are discarded on the spot and enable nothing. The legacy `preludeFizzle` warning is now DERIVED from the verdict, so the two can never diverge. Spec: `tests/preludes/preludeOutlook.spec.ts`.

**The presentation** is one pure function (`client/console/startPreludeRisk.ts`) returning badge + title + body + **the commit verb together** — a wording that says «wait» can no longer sit beside a verb that says «go», because the verb comes out of the same call. Badges: «СНАЧАЛА ДРУГОЙ ПРОЛОГ» (guaranteed) · «ПОКА НЕТ ДОСТУПНОЙ ЦЕЛИ» (possible) · «ЭФФЕКТ НЕ СРАБОТАЕТ» (final) — never a flat «СГОРИТ» over a card that is one ordinary press from working. Every enabler wears a tie («СНАЧАЛА ЭТОТ» when guaranteed, «МОЖЕТ ОТКРЫТЬ ЦЕЛЬ» when possible) — EVERY one equally, because singling one out would be the screen choosing the player's order. The `possible` copy never promises the draw helps.

**The gate** (`ConsoleStartScene`): A on a non-`playable` prelude sends NOTHING, animates nothing, moves no card and opens no empty picker — it enters the **risk stage**, an inline state of the same workspace (absolutely positioned over the queue's own slack, so the cards it is about stay visible and nothing reflows). The commit is a **HOLD** on the shared `consoleHoldConfirm` gate — a two-step press is a good guard against a misaimed press and a useless one against a fast press, and a reflex double tap is exactly the accident an irreversible action needs protection from. Its verb is «РАЗЫГРАТЬ БЕЗ ЭФФЕКТА», B is «ВЕРНУТЬСЯ К ВЫБОРУ», and the bar draws the ring (`ConsoleCommand.hold`). The stage is **derived from the focus**, so navigation, the fullscreen inspect, a minimize and an unmount all drop it by construction — the player can never return to a screen one input from losing an effect. Committing shows one short «ЭФФЕКТ ПОТЕРЯН» after the ORDINARY play animation lands; nothing else about the play changes. Guards: `startPreludeRisk.spec.ts` · `consoleHoldConfirm.spec.ts` · `consoleStartUi.spec.ts` · e2e `console-prelude-burn-gate.spec.ts`.

Three properties are load-bearing. **① The gate is EXACTLY the badge** — both are `fizzles`/`preludeFizzleNotice`, so «asks sometimes» can't happen. **② It is DERIVED FROM THE FOCUS, not latched**: `burnGate` returns undefined unless the armed name is still the focused item, so a d-pad move — or a fullscreen browse, which drives the same cursor via `zoomOriginFor`'s `onBrowse` — disarms by construction and a stale arm can never fire on a card the player has walked away from (X-inspect deliberately does NOT disarm: reading the card you are about to burn is the right thing to do between the two presses, and `onBrowse` fires only on a real LB/RB browse, never on open). **③ It never withholds the play** — burning a prelude stays a legal (bad) move; the gate costs one press, never the choice. The fullscreen viewer's A verb (`ceremonyZoomLabel`) flips to «Подтвердить» while armed, because it is the same press. Guards: `consoleStartUi.spec.ts` (the bar contract) + `tests/e2e/console-prelude-burn-gate.spec.ts` (forced Double Down + Ecology Experts deal: arms, states, B-cancels, nav-disarms, the un-badged prelude still plays on one press, and the rail's reserved height still contains the caution).
- `startGameFlowEligible/Active/AllDone/HasFocusedSubAction` — gen-1 gating, the sticky-activated mount predicate (false during `isInitialDraftAwaiting` and after `completed`), the "begin the game" gate, and the "a focused sub-action is the prompt → collapse to the pill" predicate (which DOES still match the action-menu by title — that OrOptions TITLE, unlike the corp OPTION titles, is not mutated in place).

**Drew-N-choose-ONE block (New Partner / Valley Trust).** When `startFlowPreludeDrawPrompt` is live the overlay renders the drawn candidates in a distinct "ВЫБЕРИТЕ ОДИН ПРОЛОГ ЧТОБЫ РАЗЫГРАТЬ" block, each with РАЗЫГРАТЬ. On pick, `recordDrawChoice(view.id, candidates, chosen)` saves the decision into `startGameFlowState.drawChoices` BEFORE submitting (the server discards the non-chosen immediately, so they vanish from `playerView` — this is the only chance to capture them), then the resolved block shows the chosen РАЗЫГРАНА (green ✓) and the rest СБРОШЕНА (red ✕). Per-player; cleared on `markStartFlowCompleted` / reset.

**Two minimal server additions (the only server changes):** (1) `PlayerViewModel.pendingInitialActions: ReadonlyArray<CardName>` (self-model only, from `player.pendingInitialActions.map(c => c.name)`) — signals WHEN the corp still owes its first action (drives the corp-area "awaiting" status + the completion gate). (2) the `startGamePrompt` marker above. Both serialized in `ServerModel.getWaitingFor`/`getPlayerModel`; corp identity is already public so nothing leaks. Covered by `tests/models/ServerModel.spec.ts` + `tests/preludes/StartGamePromptMarker.spec.ts`.

**Routing suppression (so the legacy surfaces don't double-render):**
- `DraftFlowOverlay.cardInput` returns `undefined` when `startFlowAnyPreludePrompt(view)` matches (both hand + draw modes).
- `WaitingFor.useModalForCurrentInput` returns `false` when `startFlowCorpPrompt(view)` matches AND `startGameFlowActive(view)` (mirrors the existing `handPlayPrompt` suppression). The corp option's DEFERRED sub-actions (Tharsis city `SelectSpace`, Poseidon/Aridor `SelectColony`, payments) arrive as NEW top-level prompts AFTER the OrOptions is answered — they are NOT suppressed and render on their normal dedicated surfaces (`PlacementBanner` / `ColoniesOverlay` / `MandatoryInputModal`); the overlay just collapses to the pill via `startFlowHasFocusedSubAction`.

**⚠️ i18n MUTATES `Message.message` IN PLACE on render — never detect a prompt by its (translatable) title TEXT.** The shared `Message` object that backs an OPTION title has its `.message` field rewritten from the English template to the active locale the first time it's rendered (e.g. `'Take first action of ${0} corporation'` → `'Выполнить начальное действие корпорации «${0}»'`). Because `playerView.waitingFor` holds that SAME object, a predicate matching on the English text silently STOPS matching after the first render — which once leaked the legacy corp `OrOptions` modal back in (suppressed on the first computed pass, un-suppressed once the title was translated). **The fix is the explicit `startGamePrompt` marker** — a structural field i18n never touches. (An EARLIER fix detected via the title's CARD data token value; the marker superseded it as cleaner/production-grade.) When you add any new prompt detection, use a server marker or another structural signal, NEVER title text. The one surviving title check — the per-turn action menu in `startFlowHasFocusedSubAction` — is safe only because that OrOptions TITLE isn't mutated (the fork's inline action UI relies on the same `'Take your first/next action'` match and works). Covered by `tests/client/components/startGameFlow/WaitingForCorpSuppression.spec.ts` (mounts the real `WaitingFor` and asserts `useModalForCurrentInput === false` regardless of the title text).

**These predicates also run inside a computed, so they MUST NOT throw.** Every array access is guarded (`(view.pendingInitialActions ?? []).length`, same for `preludeCardsInHand`) so an older server that omits `pendingInitialActions` can't `TypeError` the computed and break the render.

**Submit + lifecycle:** the overlay copies `DraftFlowOverlay`'s App-level `onsave`/`applyPlayerViewUpdate` (POST `paths.PLAYER_INPUT`, shares `root.isServerSideRequestInProgress`, always does a full `playerkey++` remount — the overlay survives it). РАЗЫГРАТЬ (grid or draw) → `{type:'card', cards:[name]}`; ПРИМЕНИТЬ ЭФФЕКТ → `{type:'or', index: corpActionOptionIndex, response:{type:'option'}}`; НАЧАТЬ ПАРТИЮ → just `markStartFlowCompleted(view.id)` (NO round-trip — the `'Take your first action'` menu is already live underneath, rendered inline since it's an `ACTION_MENU_TITLE`).

**Minimize + backdrop.** Two collapse paths share one pill (`.mandatory-input-modal-pill` chrome): AUTOMATIC (`startGameFlowState.minimized`, set when a focused sub-action owns the screen) and MANUAL (the local `userMinimized`, set by the `↗ СВЕРНУТЬ` button — `collapsed = minimized || userMinimized`). The pill click clears `userMinimized` only (an auto-minimize for a live sub-action keeps the pill). `userMinimized` resets when the actionable step changes (`stepSignature`). The backdrop is deliberately LIGHT and NOT blurred (`start_game_flow.less`) — a soft vignette, not a dark cover — so the player can read their panels and SEE the delta-chips that animate when a prelude / corp effect resolves.

**Fullscreen prelude play.** A single click on any prelude card opens it in the shared `CardZoomModal` (the card's built-in zoom is suppressed by `@click.capture.stop="openZoom(name)"` on the thumb). The `#actions` slot shows a РАЗЫГРАТЬ for PLAYABLE cards only (`playableZoomNames` = playable grid entries + live draw candidates); `playZoom` → `playByName(name)` dispatches to the draw recorder or the normal play and closes the viewer. `:cards="zoomNavCards"` (every shown prelude) gives ← / → navigation.
