# RX19 · Metal Research (Индустриалисты) — пассив, меняющий ЦЕННОСТЬ ресурса

**Статус: СДАНА 2026-09-25.** Вторая карта Индустриалистов. Выплатная половина написана дважды
до неё (сталь по влиянию — RX10, титан по влиянию — RX09/RX17), поэтому весь вес карты в одном
новом механизме: **пассив, который меняет ЦЕННОСТЬ РЕСУРСА** — пока закон принят, единица стали
участника стоит 3 M€ вместо 2, титана — 4 вместо 3. Это второй закон, вмешивающийся в экономику
после скидки RX14, и он опаснее: скидка — вычисление, а ценность ресурса в этом движке —
**изменяемое сериализуемое ПОЛЕ игрока**. Главное решение карты — это поле не трогать.

Печатный текст: «При принятии: получите сталь и титан, равные вашему влиянию. Эффект: каждая
единица стали и титана стоит на 1 M€ больше.» Задание председателя: повысьте производство титана
на 1 (квадрат титана в коричневой рамке = производство, §4.1.1 спека). Дополнений не требует.

Промт: `docs/claude/prompts/resolution-rx19-metal-research.md`. Файл карты:
`src/server/parliament/resolutions/industrialists/MetalResearch.ts`.

## 1. Главный принцип: надбавка НА ЧТЕНИИ аксессора, поле не трогать

`Player.steelValue` / `Player.titaniumValue` — приватные поля (2 / 3), которые поднимают
`increaseSteelValue()` и родня («Улучшенные сплавы», «Реголитовые пластики», …), опускает
`decreaseSteelValue()` с полом `> 0`, и которые **сериализуются** (`SerializedPlayer`). Читают их
только два аксессора — `getSteelValue()` / `getTitaniumValue()`.

Закон встаёт в тот же шов, что скидка RX14, — как **чистый ЗАПРОС**, а не как мутация:

| Слой | Что добавлено |
| --- | --- |
| Контракт пассива | `ResolutionPassive.resourceValueBonus?(player, resource): number` — M€, которые закон ДОБАВЛЯЕТ к тому, что покупает одна единица; 0, если не применяется. Чистая функция: не мутирует, не логирует |
| Диспетчер | `ParliamentHandler.resourceValueBonus(player, resource)` рядом с `cardDiscount`: принятая карта, её хук, `parliament.participates(player)`; области события НЕ открывает — здесь ничего не платится, только читается |
| Аксессоры | `getSteelValue() = steelValue + запрос(STEEL)`, `getTitaniumValue() = titaniumValue + запрос(TITANIUM)` — ОДИН читатель поля для цены |
| Карта | `metalResearchValueBonus(player, resource)` = 1 для стали и титана, 0 для всего прочего |

**Почему не через поле.** Соблазн — на принятии вызвать `increaseSteelValue()` каждому участнику,
на смене закона `decreaseSteelValue()`. Четыре причины, по которым это запрещено:

1. поле СЕРИАЛИЗУЕТСЯ — загрузка посреди действующего закона обязана НЕ применять надбавку второй
   раз, а это «помни, что уже начислил», то есть второе состояние рядом с первым;
2. `decreaseSteelValue()` имеет пол и не знает, ЧЬЮ единицу снимает: закон, снятый после того, как
   игрок потерял ценность иначе, заберёт чужое или не заберёт своё;
3. игрок, вступивший позже, закон, принятый повторно через поколения, отмена фазы — каждый путь
   рассинхронизирует пару «начислил / вернул»;
4. дрейф невидим: цена просто тихо неправильная, и никакой гард на это не встанет.

На чтении всё это исчезает по построению: поле никогда не пишется, формат сохранения не меняется ни
на байт, сохранение из-под закона грузится правильно (спек: в поле 2 / 3, на аксессоре 3 / 4),
закон, покинувший ENACTED, забирает надбавку с собой в тот же момент, что и слот, — «отката» нет,
потому что ничего не «накатывалось». Аддитивность бесплатна: «Улучшенные сплавы» под законом — 4 / 5,
и в поле при этом лежит только шаг карты (3 / 4).

## 2. Сырые читатели полей — прочёс `src/`

`grep steelValue|titaniumValue` по всему `src/` (кроме `getSteelValue` / `getTitaniumValue`):

| Место | Что это | Решение |
| --- | --- | --- |
| `Player.spendableMegacredits()` — ветка Luna Trade Federation, `this.titaniumValue - 1` | **сырое чтение**: проверка «хватит ли денег» расходилась бы с ценой `payingAmount` | переведено на `getTitaniumValue()`; спек «`spendableMegacredits` согласен с `payingAmount` и `canAfford`» |
| `Player.serialize()` / `deserialize()` | поле как поле — своё значение игрока | намеренно ПОЛЕ (комментарий у объявления и в `serialize`) |
| `Merger.spendableMegacredits` (`titaniumValue - 1`) | локальная переменная от `player.getTitaniumValue()` | уже аксессор |
| `behavior.steelValue` / `titanumValue` (`Behavior.ts`, `Executor.ts`, карты) | декларативный ФЛАГ карты, не поле игрока | не трогается |
| `PublicPlayerModel.steelValue` / `titaniumValue` и клиентские чтения (`paymentPlan.rateFor`, `railValueModel`, `PaymentWidgetMixin`) | чтения МОДЕЛИ, которую кормит `ServerModel` через аксессор | правильны по построению |

## 3. Что пришло бесплатно, и чем подтверждено

| Потребитель | Читает | Подтверждено |
| --- | --- | --- |
| `payingAmount` → цена | аксессоры (сталь, титан, floodgate-сталь) | юнит: 2 стали = 6, 2 титана = 8, floodgate 2 × 3 |
| `canAfford` | `payingAmount` | юнит: 4 стали без M€ покупают 12 под законом, не без него |
| `checkPaymentAndPlayCard` | `payingAmount` | юнит: «Ядерная энергия» (10) за 4 стали — принято под законом, «Did not spend enough» без |
| `spendableMegacredits` | аксессор (после прочёса) | юнит: 5 + 2 × (4 − 1) = 11 = `payingAmount` |
| Luna Trade Federation | множитель − 1 ПОСЛЕ ценности | юнит: 4 − 1 = 3 вне космоса, 4 на космической карте |
| `PublicPlayerModel.steelValue / titaniumValue` (`ServerModel`) | аксессор | юнит: `Server.getPlayer` = 3 / 4 у каждого участника, 2 / 3 без закона |
| `paymentPlan.rateFor` (панель оплаты, редактор) | модель | клиентский юнит «под законом» 3 / 4, LTF 3; **e2e: строка стали композера «×3»** |
| МС-бейджи рельсы (`railValueModel`) | модель через `rateFor` | клиентский юнит 3 / 4 и «4/3» с LTF; **e2e: бейджи 2 → 3 и 3 → 4 в момент принятия, без перезагрузки** |
| `effectForecast.paymentValues` (floodgate-сталь) | аксессор | юнит: `value: 3` под законом, 2 без |
| `recordPaymentValueBonus` | аксессор − база, атрибуция ТОЛЬКО картам с `behavior.steelValue` | доля закона честно не атрибутируется (как у императивных модификаторов — прежний комментарий); карта с флагом получает ровно свою единицу |
| `Merger`, `IndustrialComplex` | `getTitaniumValue()` | аксессор даёт 4 под законом (юнит аксессора); сюиты карт зелёные |
| `PaymentWidgetMixin` | модель | живого потребителя нет (`StandardProjectPaymentContent.vue` не монтируется — замороженный desktop) |

## 4. Двойник прогноза у ценности — сам РЕЙТ, а не факт

Прецедент RX14 дословно: у скидки двойник — разбор цены. У ценности двойник — рейт там, где
принимается решение: бейдж рельсы и «×3» в строке оплаты читают ту же модель, что и сервер
считает цену. `forecast` карты возвращает `[]`: факт напечатал бы то же число второй раз, в группе
для триггеров, и ему не нашлось бы пары `effect-triggered`. Спек закрепляет: разбор цены НЕ
тронут (`discounts: []`, `final === base` — ценность не скидка), фактов резолюции в прогнозе нет.

## 5. Две выплаты — два шага, две записи

Сталь = влияние и титан = влияние — `DEVELOPMENT_CRAZE_STEEL` и `JOVIAN_TAX_RIGHTS_TITANIUM`
дословно (спек сравнивает объявления `deep.eq`). Шаги `steel` → `titanium` в печатном порядке,
каждый под источником резолюции, одна строка журнала на часть, влияние 0 — **два названных
пропуска** («No influence» на каждом шаге). Семейство стенда — `influence`; стенд, панель голосования
и заседание рисуют ДВЕ строки через общий `voteYieldsOf` над `scaled` (клиентский юнит).

## 7. Что это оставляет следующим картам

Пассив-ЦЕННОСТЬ — теперь член семейства: следующий закон, меняющий стоимость единицы, объявляет
`passive.resourceValueBonus` и текст, всё остальное приходит из шва. Условие от ИГРОКА (а не от
ресурса) читается там же — хук получает и его. Отрицательная надбавка (ценность МЕНЬШЕ) шва не
имеет: `ParliamentHandler.resourceValueBonus` обрезает результат нулём снизу — понижение потребует
своего решения о поле с полом `> 0` и о том, чей шаг оно съедает. Ценность прочих ресурсов (тепло,
растения как M€) живёт на флагах `canUse*AsMegacredits`, а не на этом шве.
