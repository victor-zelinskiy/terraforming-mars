# Client UI rules

## NORTH STAR — global `createVaporApp(App)` (the owner / the architect, 2026-11-12)
The client is going to ONE Vapor application on Vue 3.6 (`createVaporApp(App).mount('#app')` — no virtual DOM, every component a Vapor component); **rewriting the existing components is in scope and the Options API is being left behind.** Staged — V1 the pilot (`vue@3.6.0-rc.15`, pinned exactly) → V2 architecture v2 to the end → V3 the rework of all components, wave by wave under the full CI e2e → V4 the switch. Program, counted inventory, protocols: `docs/claude/vapor/ROADMAP.md`. What it asks of the diff in front of you:
- **A NEW `.vue` is `<script setup lang="ts">`** — never a new Options-API component (`props` → `defineProps`, `emits` → `defineEmits`, state → `ref` / `reactive`, `computed()`, `watch()`, a template ref instead of `this.$refs` / `this.$el`, `nextTick()` instead of `this.$nextTick`, its timers in `const flow = useFlowScope('<kebab-name>')`).
- **A conversion is done BY THE BOOK — `docs/claude/vapor/RECIPES.md`**: print the component's sheet (`node scripts/vapor/inventory.mjs --component <path>` — its constructs with their recipe ids, what it MUST EXPOSE to the parents that reach it through a ref, who mounts it), apply the rows it names in the order of the book's § 1 (declarations → watchers in the block's order → hooks → `defineExpose`), run the checks of its § 0. The book is complete by check (`tests/console/vaporRecipes.spec.ts` — the inventory fails on a construct with no recipe): if you meet something it does not cover, the recipe is written FIRST.
- **A custom directive is ONE imported binding for both runtimes** (`@/client/directives/vDirectives`: `vI18n` · `vTrimWhitespace` · `vEmbedZone` · `vStripActionPrefix` · `vStripEffectPrefix`); a NEW one is written with `dualDirective({mounted, updated?, unmounted?})` (`directives/dualDirective.ts`) — Vapor refuses an object of hooks, the virtual DOM gives a function no `unmounted`.
- **Never the instance's internals** — `this.$.uid` / `.isUnmounted` / `.subTree`, `$options`, `$forceUpdate`, `$data` (the readiness ledger's `instance-internals` row): an id is a module counter taken in `setup`, «am I gone» the component's own `onUnmounted` flag, a watcher's body a NAMED function its other callers call.
- **Do NOT convert an existing component in passing.** Its conversion is a commit of its own in its V3 wave, verified by its surface's e2e specs. Touching an Options-API component for a feature or a fix, you stay in its form — and move LOGIC out of it (below) rather than adding to it.
- **Add nothing the target has no place for**: a mixin, `$parent` / `$root`, a new `app.config.globalProperties` member, a new global `app.component` / `app.directive` registration, a render function (`h(…)`) where a template will do, a `$refs` reach from one surface into another, a new `getCurrentInstance()`.
- **Logic goes OUTSIDE the component**: state and flows in a module / a controller / a composable on the flow kernel (`createFlowRun` · `deriveFlowRun` · `scopedState` · `sessionState` — `docs/claude/console/architecture-v2/REVIEW.md` §1). The less a component holds besides its template, the less there is to convert — and the less there is to break.
- **The e2e hooks (`data-*`, classes, RU copy) are the contract a conversion keeps** — `CLAUDE.md` invariant 14.
- **V1 landed (2026-11-12): the runtime is `vue@3.6.0-rc.15`** — an EXACT pin plus an `overrides` block that keeps every `@vue/*` core package on the same version (a prerelease satisfies no peer range; without it npm installs a second, 3.5 compiler). Bumping it is the protocol of ROADMAP §3.8, never a caret.
- **A `<script setup>` component IMPORTS what the Options API got from the app**: `import {$t} from '@/client/directives/i18n'` · `import {vI18n, vTrimWhitespace} from '@/client/directives/vDirectives'` (ONE binding per directive that both runtimes call — the line does not change when the component gains `vapor`) · every component it renders. The template keeps `$t(…)` and `v-i18n` as they are. A `<script setup>` component that leans on a global is a red row of the readiness ledger.
- **`<script setup vapor lang="ts">` (step B) is taken per the book's § 0**: the component's sheet prints a clear `STEP B` line, each «at B» note of its rows is addressed, and a shape the capability suite has not proven gets its row in `tests/client/vapor/vaporCapability.spec.ts` FIRST. Until V3's waves start that means LEAVES (the pilot's three); a host of other components takes step B in its wave. Inside a Vapor component: no `getCurrentInstance()` (it is `null`), no global properties, a parent's `ref` sees only what `defineExpose` gives, `v-memo` is ignored — and **the template STARTS WITH ITS ROOT** (no `<!-- … -->` before it: a development build keeps the comment, the root becomes a fragment, and the attributes the parent lets fall through are dropped — in dev and in unit specs only; say it in the script block; guarded). The three shipped examples: `marsbot/BotReviewEdgeNotice.vue`, `console/ConsoleForecastDoor.vue`, `card/CardDescription.vue`. After adding or converting one: `npm run ready:vapor` in the same diff.
- **ONE MUTATION — ONE REACTION.** Two watchers (or a watcher and a computed-driven reaction) that read ONE array / Map / Set through different facets — its `length` / `size`, its iteration (`find`, `some`, `for…of`), one key — are woken by a single mutation in an order that is NOT a contract of Vue (3.5: length first; 3.6: the key, then iterators, then length). If the order matters they are ONE `watch` whose source reads both and whose body does the two things in the order you mean (`marsbot/marsBotPresentation.ts` is the model). Guard + the full list of what IS a contract: `tests/console/vueReactivityContract.spec.ts`, `tests/client/console/vueTickOrder.spec.ts`.
- **The three ledgers of the client**: `kernelCoverage` (nothing waits outside a scope — empty) · `architectureDebt` (what still runs on a mechanism the kernel replaces — frozen) · **`vaporReadiness`** (what the target has no place for: an Options-API component, `getCurrentInstance`, `$parent`, a mixin, a global registration, a render function, `v-memo`, `$refs`, a global in `<script setup>` — frozen per file, a new file starts at zero, a Vapor component stays Vapor).

## Desktop UI is BEING DELETED in waves (policy 2026-08-22; frozen since 2026-07-15)
The fallback guarantee is DROPPED: the future desktop UI will be built FROM the console shell, so frozen desktop code is dead weight scheduled for deletion, never a surface to fix. **Wave 1 (done)**: console unconditional (`consoleModeState.enabled` always true; `?console=0` / stored `tm_console_mode='0'` never read again; the settings shell switch and hold-Menu toggle removed), App.vue no longer references `PlayerHome` or the desktop-only overlays. **Wave 2 (done)**: `WaitingFor.vue` is HEADLESS (poll chain + submit funnel + cinematic holds + the `SelectSpace` board binder — zero prompt rendering); the radio/modal input stack is DELETED (`PlayerInputFactory`, the leaf renderers, `MandatoryInputModal`, `ModalInputHost`, `PlayerHome`, `Sidebar`, the playgrounds, the spectator feature); the degenerate `projectCard` prompt renders natively in `ConsoleTaskHost` (pick → pay); standard projects/actions moved to the premium face. Remaining frozen files go by import graph in later waves (floors, locales and the upstream-sync «keep deleted» policy ride those waves).

**Wave 3 (done)**: the unreachable desktop subgraph deleted by import graph (desktop journal/overlays/TopBar chain/initialDraft, desktop main menu + create screens; `/new-game` lands in the console creator). **Wave 4 (done)**: CEOs joined the premium face and the legacy `Card.vue` renderer family is DELETED — `CardFace.vue` (the facade every host imports) is premium-only; the render-DSL `CardRenderData` tree STAYS (shared by journal popovers, MarsBot faces, effect chips).

**The transport rework (post-wave-4)**: `WaitingFor.vue` is DELETED. The game transport is the `console/transport/gameTransport.ts` MODULE (poll chain + `submitInput`/`submitBatch`/`cancelPlacement` + the cinematic holds + view apply); `ConsoleBoardBinder.vue` owns its lifecycle and renders only the legacy `SelectSpace` board cell-binder. The WS channel (realtimeService, default-ON end to end) is the primary update signal; the poll is the bounded fallback.

**The board-input rework**: `SelectSpace.vue`/`GoToMap.vue` are DELETED — `ConsoleBoardInput.vue` (components/console) is the console-native cell-binder (same live machinery: availability/illegal classes + BRD-3 mirrors, premium hover popovers, the confirm dialog, the one `armTilePlacement` point, surgical teardown). **No load-bearing legacy file is left** — everything the console stands on is console-native or `@console-shared` (below).

Markers: `@deprecated Desktop-only UI (frozen 2026-07-15)` vs `@console-shared`; full inventory `docs/DESKTOP_DEPRECATION_AUDIT.md`.

**The SHARED layer is not deprecated** and keeps full quality bars: `src/common/` models, pure view-models (`victoryPointsModel`, `effectSummary`, `insightEngine`, `endgameFacts`, `journalView`, …), module reactive state (`journalState`, `notificationState`, `presentationFlow`, …), the premium card face (`.pcard`), `motionTokens`.

## Timers and frames — nothing in the client waits outside a scope
**No raw `setTimeout` / `setInterval` / `requestAnimationFrame` / `gsap.delayedCall`-as-a-timer / VueUse timer helper (`useIntervalFn`, `useDebounceFn`, …) anywhere under `src/client`** — the console and the shared layer alike. Every wait has an OWNER on the flow kernel and is a row of its wait table: a component's (`setup() { return {flow: useFlowScope('<kebab-name>')}; }` → `this.flow.after(…)` / `.afterFrame(…)` / `.guarantee(…)` / `.every(…)`; the scope is lazy and parented by where the component stands — a shell's session inside the game, the page's outside), a module flow's run, the session's (`consoleSessionScope()`), or the page's (`consoleAppScope()` — a service that lives across games: the realtime channel, the lobby, the boot). Decide PACING (`after` — must NOT run once the owner is gone) vs RELEASE (`guarantee` — must run even then) before typing. The ledger `tests/console/kernelCoverage.spec.ts` is EMPTY and fails on the first raw primitive in a new or old file; the only two declared exceptions are the gamepad's device clocks. Full contract: `.claude/rules/console-flow.md` § Timers, frames and runs; `docs/claude/console/architecture-v2/KERNEL.md`.

## Update model — NO remount
The game subtree (`<ConsoleShell>`) lives for the whole session; a response applies `playerView` reactively.
- **`playerkey` is the transient-UI RESET EPOCH, not a `:key`.** New transient UI state that a submit must clear MUST be reset via the epoch (module states register reset callbacks) — never assume a remount clears it.
- **Structural sharing** (`viewSnapshotShare.ts`): the root identity always changes, unchanged children keep their refs. **Never add an identity-watcher expecting per-response firing on a SUB-object of `playerView`** — watch VALUES (`gameAge`, `undoCount`, the concrete field).
- Anything that used `mounted()` to re-derive per-response state uses a value-based watcher instead.
- Rollback: `?patch=0` (no structural sharing). The `?remount=1` / `tm_remount` legacy keyed remount was RETIRED (2026-08-23) — `legacyRemount.ts` is deleted and nothing keys on `playerkey`. The baseline modules (`accentBaseline`, `tileBaseline`, cube baseline) stay — the live board diffing / hydration paths read them, not dead code.

## Prompt detection + submission (load-bearing)
- **Availability is SERVER-authoritative.** Walk the `waitingFor` `OrOptions` tree; the option's PRESENCE is the source of truth. Submit via `gameTransport.submitInput()` with the nested `OrOptionsResponse` payload — byte-identical to the historical radio UI, no server change. Never re-derive availability from raw player state.
- **⚠️ NEVER detect a prompt by its title text.** i18n mutates `Message.message` IN PLACE on render, so an English-text match silently stops matching after the first render (this leaked a legacy modal back in). Use a server marker (`startGamePrompt`, `choiceContext`, `placementContext`, `awardFundingPrompt`, `reveal`) or another structural signal. The one surviving title check (the action menu) is safe only because that title isn't mutated.
- Show a blocked action DISABLED with a reason, not hidden.
- **The transport renders nothing.** `gameTransport.ts` owns poll/submit/holds/view-apply; `ConsoleBoardBinder` mounts only the `SelectSpace` cell-binder. Never add UI to the transport, never submit around it.

## Tooltips — the native `title` attribute is BANNED
Use the shared `.premium-tooltip(@max-width)` LESS mixin + `:data-hint`. **Host `data-hint` on a NON-disabled wrapper** — a disabled `<button>` never fires `:hover`, and that is exactly where a "why disabled" hint is needed. Every disabled control must carry a reason. The mixin forces `position: relative`.

**Disabled visuals:** never dim with whole-element `opacity` (goes see-through over the board) — dim via `filter` + muted text, keeping the element opaque.

## Hosting a `<Card>`
- Import **`card/CardFace.vue`** (the facade), never legacy `Card.vue` directly.
- A clickable wrapper that opens its own fullscreen MUST suppress the card's built-in zoom with `@click.capture.stop`, else two viewers open.
- A persistent `<Card>` that re-points across cards needs `:key="cardName"` (legacy `Card.vue` resolves render data in `data()`).
- **Centering UI under a card:** `.card-container` has an asymmetric legacy margin (`15px 30px 10px 0`). Zero it in your wrapper scope (`.your-slot > .card-container { margin: 0 }`) — never compensate with a negative margin (it drifts across zoom breakpoints). Inter-card spacing belongs to the parent's `gap`.

## State that must survive the reset epoch
Per-game UI state (overlay open flags, filters, selections, picks) lives in **module-level reactive files** (`journalState`, `playedCardsViewState`, `handFilterState`, `actionsOverlayState`, `sellPatentsState`, …) and panels that must outlive it are mounted at **App level**, not inside PlayerHome.

## The LOBBY («Мои партии») — a source has a STATUS, and «пусто» is one of four answers
The game listing is ONE model (`mainMenu/lobbyState.ts`) over N SOURCES — this device's server plus every LAN host; `lanState.ts` is discovery only (who is out there), never listing. Four rules, each of which shipped broken once:
- **`idle` ≠ `loading` ≠ `ok` ≠ `unreachable`, and «У вас пока нет партий» may ONLY be rendered for `ok`.** A never-asked list, a failed fetch and an empty library used to print the same sentence, so a party that existed read as one that did not.
- **The identity is an INPUT, not a precondition.** It can arrive after the first frame (Steam prefill, profile roster); a screen that reads it once in `mounted()` and never watches it needs an APP RESTART to recover. `setLobbyIdentity` is the reload path.
- **Opening the screen is an unconditional REFRESH** of every source; a cross-session cache seeds the first paint and never satisfies a load. Push (`lobbyChannel.ts` → the realtime LOBBY room) is primary, the poll is a self-re-arming floor (30 s live / 5 s otherwise while open).
- **Nothing disappears silently:** a failed refresh keeps its rows; a LAN host that stops answering keeps them marked + un-enterable for a few rounds; only discovery dropping the host removes them at once.
⚠️⚠️ **And the LAN half is not a client problem at all: mDNS FINDS a host, a SOCKET says it is still there.** `bonjour-service`'s Browser emits `up` ONCE per service and never re-announces one it already holds, so a «last seen» fed from it freezes at discovery — the TTL sweep reading it deleted EVERY host 45 s after finding it, permanently, and only an app restart brought it back. That was the actual bug behind «партий по локальной сети не видно»; reworking the client did nothing for it. `lanDiscovery.ts` now re-reads presence from `browser.services` and decides liveness with a raced TCP connect — all of it in one sockets-free engine (`HostRegistry`) whose four invariants are: presence is ADDITIVE (an empty browser list removes nothing — `rebuildLinks()` on a Wi-Fi/VPN change makes it empty), only a socket removes, a hidden host keeps its own record and retries, one row per machine. The LAN section speaks in all three states (unreachable + REASON · answered-but-no-seat-with-your-name · stale) and «＋ Добавить хост по адресу» is the way in when multicast is blocked. The list is sorted **strictly by creation time, newest first**, and every row says how long ago it was created — the age is what makes the order legible, so the client sorts rather than inheriting a server's order, and ONE reactive clock (`lobbyState.nowMs`, re-armed at the freshest row's cadence, alive only while the screen is) moves every label in the same tick. **«Мои кампании» obeys the same rule on BOTH tabs** (`sortCampaignsNewestFirst`; the row's age is the CREATION age, and the screen hands its rows to that one clock via `setLobbyAgeRows`) — its sort once led with a priority band (action required → launch-ready), and since a mission's turn flips the row's state on every move, a fresh campaign sat on top one visit and at the bottom the next. What needs the player is marked ON the row, never by where it stands. ⚠️ Timers here are OWNED waits of the page's scope (`consoleAppScope().after` / `.guarantee` / `.every` — the lobby lives as long as the page, never a game session; § Timers and frames below): no handle pairs to keep, and nothing leaks into a later spec. Every trigger funnels into `refreshLobby()` — adding a trigger must never mean adding a loading path. Server side: `models/lobbyIndex.ts` (a per-game record + a revision; `IGameLoader.peek()` exists so a bulk sweep never `touch`es the cache). Full contract: `docs/claude/my-games-lobby.md`. **Its SURFACE is a screen of game CARDS, never a dialog** (TR68 — `ConsoleLobbyScreen` + `ConsoleLobbyCard` over the pure `console/menu/lobbyCardModel.ts`; `docs/claude/console/pregame-showcase.md`): every state above stands on the stage, never as a line in an empty plate.
