# Animation rules

## One motion system — no hand-rolled durations
`src/client/components/motion/motionTokens.ts` is the single source of animation speed. JS timings resolve through **`motionMs(base)`**, CSS animations through **`calc(<base>ms * var(--motion-scale, 1))`**, easing from **`MOTION_EASE`**. Presets `calm|standard|swift` (`?motion=`, `tm_motion_speed`); rAF loops use `createFrameGate` (`?motionFps=`). `prefers-reduced-motion` is a separate overriding axis and must be honoured.

Taste: Ark Nova (BGA) feel — short easings, subtle scale, no hard pop-ins, calm by default. Never introduce flashy motion just because something changed. **Light is not a default accent**: a glow may mark a ONE-SHOT event the player must not miss and must end on its own; a standing state is never a halo and never a breathing loop (CLAUDE.md invariant 15, `console-ui.md` § VISUAL RESTRAINT, guard `glowRestraintGuard.spec.ts`).

## Animation holds — never a timer, never an ad-hoc gate
Every CRITICAL animation is a first-class foreground occupant via `presentation/animationHold.ts`:
- `registerAnimationHoldSupplier(label, predicate)` at module scope for a flow with a reactive "scene owns the foreground" predicate, or `beginAnimationHold(label)` for a component beat (idempotent release from every exit path).
- **⚠️ A SUPPLIER PREDICATE MUST READ VUE-REACTIVE STATE. A plain module `let` KILLS the whole registry.** The live count is a `computed` and the 35 s ceiling is a `watch`, both over predicates the registry does not own — a non-reactive read invalidates neither, so the count sticks at whatever it last was: `foregroundBlockReason()` returns `'animation'` forever with NOTHING holding, the ceiling never arms, and no expiry can cure it (reading the predicate directly correctly says false → "expired nothing", warn `leaked hold: none named`). This shipped as a dead game (`hand-delivery`'s `activeRuns`). Net under it: the console watchdog calls `refreshAnimationHolds()` every 1 s tick, and a count with zero live labels is treated as a provable phantom. **Since 2026-09-12 that same sweep also RECONCILES the ceiling** (predicate true with no timer → arm; false with a stale timer → disarm quietly) — a missed reactive edge costs at most one tick, in both directions (field log: `tile-placement-remote` fired a 35 s «force-released» over an idle module — the degrade path drains the plain-array queue with no reactive write). The predicate contract still stands: the sweep bounds a leak, it does not make a non-reactive term correct (the count itself can still lag up to 1 s).
- **⚠️ A SCENE THAT CAN WAIT FOR A COVERED BOARD: THE WAIT OUTRANKS EVERY TERM, AND THE STAGE COMES DOWN ON THE PARK.** The remote queues (`tile-placement-remote`, `nomad-move-remote`) park their next event while a workspace covers the board — and the workspace's own follow-up (a card action's draw: «Берём карты из колоды…») waits for the blocking holds. The predicate read `onStage || (!waiting && queued)`, and `onStage` stayed up from the PREVIOUS event of the same queue, so the second event's wait held the screen: a deadlock only the 35 s ceiling ended (field log 2026-10-23, «Коммерческая сеть»). The form is `!waiting && (onStage || queued)`, and parking clears the last event's stage (`parkForBoard` — never at every event's end: the last landing's splash still plays on those elements over a board in view). Guard: `tests/client/components/console/remoteBoardQueueHold.spec.ts`. A NEW queue that waits for the board copies both halves.
- Wrappers: `holdAnimationWhile(label, promise)`, `holdForGsapAnimation(label, tl)` (releases on completion AND on kill via a chained `onInterrupt`).
- **The release IS the flow's own completion signal (GSAP `onComplete` → the reactive flag drops) — NEVER a `setTimeout`.** A 35 s ceiling force-releases a leaked hold with a warn; a hold the watchdog has to recover TWICE is quarantined for the session.
- **⚠️ The ceiling MASKS the hold — it cannot fix the owner's state. A supplier whose module has an abort/recall MUST register it as `expire`** (+ a `diagnose` snapshot): the field wedge 2026-09-10 had `hydro-marker` and `tile-placement-remote` each «force-released» at 35 s while their module state stayed frozen — every input gate and close gate reading that state directly stayed wedged behind a hold the registry had stopped counting. `expire` runs the owner's own recovery on the ceiling AND on the watchdog's expiry, so the ceiling ends the WEDGE, not just the count.
- **⚠️ Any promise you `await` around a GSAP animation MUST settle on `onInterrupt` too, not just `onComplete`.** A killed tween (unmount, `killTweensOf`, overwrite, teardown) never fires `onComplete`, so the `await` hangs forever, the enclosing `finally` never runs, and its bookkeeping leaks permanently — that is how `handDeliveryDirector`'s `activeRuns` pinned a `'notification-only'` hold true for a whole session and froze the event queue. Copy `holdForGsapAnimation`'s chained-`onInterrupt` pattern (never clobber an existing handler).
- Scope `'blocking'` by default; `'notification-only'` only for a cinematic that runs INSIDE a mandatory surface (a blocking hold would unmount its own stage — self-deadlock).
- **A new hold that hides the console task host while the server waits must add its DOM root to the leak detector's `SERVING_SURFACES`.**
- Never write a local `setTimeout` gate or an ad-hoc OR-chain in a shell computed.

## One foreground item at a time
`presentation/presentationFlow.ts` sequences client-side delivery: blocking surfaces acquire/release a **lease** around their EFFECTIVE visibility (release fns idempotent, watchers keep them in lockstep); notifications are serial FIFO with a MONOTONIC lifecycle (created → prepared → queued → presented; a blocker gates only queued → presented — a PRESENTED card is never re-queued, evicted or semantically upgraded; it leaves only by its own timer or the player’s B — docs/claude/notifications.md § ATOMIC DELIVERY). A new flow-holding item sets `holdsFlow` on its `NotificationModel`. `presentationPolicy.ts` holds the pure vocabulary and is unit-tested.

**A lease is a CLAIM that a surface is VISIBLE — derive it from the same expression as that surface's `v-if`, never a hand-written superset.** Every desync froze the game permanently (the queue can't drain, no mandatory surface can mount, and the leak detector's guard is disarmed while an announce gate holds). Two shipped that way: the reveal lease ignored the overlay's `!playedHeroHolds`, and `taskHeldForWorkspace` is documented "render nowhere" yet still held one. The net is `consoleForegroundWatchdog.ts` (leak-detector check 3): claimed + nothing rendered + something waiting, for 3 passes on the board home → the claims are EXPIRED (masked until they go honestly false — `animationHold`'s semantics), the queue drains and it names what it expired. **Note the admission signals bypass the 35 s animation ceiling entirely** — `admits(...)` reads raw scene predicates, so a leaked flow flag holds every prompt closed until the watchdog masks it.

Bot turns are notification-first with staged visual commits (`marsBotPresentation.ts`); read the archive, never re-derive scripts.

## Landing rects are RESTING rects; source rects are RAW — and BOTH are VISIBLE
**«Измерим» ≠ «видим» (the polish remediation iteration № 1, 2026-10-11).** A rect is a flight end only if the element is PAINTED where the player looks: mounted, not hidden up the chain, effective opacity ≥ 0.5, in the viewport, and not covered by a foreign band surface's glass — `resourceTransfer/transferEndVisible.ts` is the ONE verdict, every resource-transfer anchor ladder takes the first VISIBLE match, and an end that fails it is no end (the transfer degrades to the counter's tick and names the reason). The satellite under the composer's opaque glass (PL-137) measured perfectly and was «пустота» on the TV. A destination COVERED by a surface that is about to leave is WAITED FOR, not dropped (PL-165 — a DETACHED flight: born on its source, popped, waiting in the app-level layer, its arc planned only once the destination is painted; opt-in `detachCovered`). Law + guards: `console-ui.md` § THE ENDS OF A FLIGHT ARE VISIBLE. **…AND LIVE** (T06): an end is an OBJECT (`TransferEnd`) re-measured at the birth, on the final approach (`TRANSFER_RETARGET_AT`, the difference ramped in) and at the touchdown — a point cached at the press is never a landing; gone → a stand-in of the same object or absorbed in place, never the old pose (`docs/claude/console/resource-transfer.md`). **…AND PAINTED ON TOP** (T12 / CA): a visible end is not enough if the token is painted UNDER it — a flight's two ends live in different paint, so a board-born token under a workspace starts in the transfer layer's SHADED TWIN and is handed to the LIT layer (the top of the cockpit) where its box leaves the covered opening, the same element, ramped up from the shade's paint; the demotion axis is the DESTINATION, never the source (`resource-transfer.md` §7, the z map `flightLayerZOrder.spec.ts`).
`cardFlight/landingRect.ts` is the ONE answer to «where will this element rest?». A flight's **LANDING** is measured with `restingRectOf(el)` — it subtracts the element's own inline pure translation (the GSAP case) AND un-maps every live CSS animation/transition on the element or an ancestor toward its END keyframe (an entry → identity; a retargeted transition → its destination, which is what makes a mid-page-turn album slot aim at the final berth). Static positional transforms (translate(-50%) centring, the album's page berth) have no live animation and are never touched. A **SOURCE** is measured RAW (`getBoundingClientRect`) — the proxy must be born over the pixels the player currently sees, never over the rect the card will occupy later. Mixing the two up is a visible defect on BOTH sides: a resting source teleports the proxy at spawn; a raw landing snaps the card at the handoff (measured 26×9 px @1080 / 61×18 px @4K before the fix). The pure un-map math is spec'd in `tests/client/console/landingRect.spec.ts`.
`extractPlayRewards` (`resourceTransfer/resourceTransferModel.ts`) turns a play preview into transfer specs. A card-resource gain reaches it two ways: an `ActionEffect` chip noted `'to a card'`, **and** a bespoke card-target STEP (`actionPreviews.selectCardStep` with a positive `amount`) that carries no chip at all — the whole Freyja Biodomes / Venusian Plants family, whose resources used to land on the target with no flight. The step is authoritative by the same rule `selectCardStep` already trusts to derive `vpBox` from that amount. **The resource is the PICKED card's own `resourceType`** (read off the step's candidate models), because a card that adds "a microbe or an animal, depending on your choice" has no honest icon up front. Excluded: `repeatAction` picks (candidates are actions) and `copyProductionBox` picks (handled as production).

**…and a flight's SCALE ratio is measured against the box its base scale describes.** The played-card hero lifts (×1.05) before it flies, and its path is planned from the LIVE (lifted) rect — right for position, wrong for scale: `target.w / liftedSource.w` multiplied onto the rest-box base landed every card 4.8 % short of its slot (and offset by half that on each axis) on BOTH play doors, which the handoff then had to correct over an already painted card (the reported «рывок»). `planHeroPath` takes `sourceRest` for the ratio; the flight re-reads the landing place's rest rect ONCE on its final approach (`HERO_RETARGET_AT`) and bends the remainder onto it, so no correction is ever needed after the touchdown. **The handoff is reveal → hide the proxy on the NEXT frame**, never a crossfade, and the proxy wears the DESTINATION's face (tier + live model) from the apex on — two identical frames. Witness: `tests/e2e/console-play-landing-geometry.spec.ts` (hand ×3 profiles + the start queue; ≤ 1 px at the boundary, zero post-reveal motion, zero twin frames).

## A BIRTH IS PAINTED BEFORE THE FLIGHT STARTS — two clocks must not pick the first frame
A chip set at its source with `autoAlpha: 0` and flown by a timeline is first PAINTED wherever the timeline is at the first painted frame — and two clocks that are not the chip's own decide that: GSAP's global time advances ONLY at a tick (a timeline created inside a long task starts at the LAST tick — the response's own 146 ms `Response.json().then` on the Habitat Science ledger), and a SLOW FRAME lands the first tick after a correct start a whole frame later (a headless 4K frame is hundreds of ms). Both painted the M€ chip 40 % along its arc, above the panel, born out of nothing — red for days as «…born in Luna's own bonus cell» and blamed on the spec. `resourceTransferDirector.bornThenFlown`: after the wave's stagger, ON a tick, the chip turns visible at its source (the first frame of the pop); the flight's timeline is built on the NEXT tick (`gsap.ticker.frame` advanced — a painted frame between them); a kill cancels both. Whatever the frames cost afterwards, the first thing the player sees is the source. Guard `tests/console/transferFlightClock.spec.ts`. A NEW director whose first frame must be the source (a birth, a lift-off) does the same.

## A GAIN IS SHOWN ARRIVING — the reward on the rail, and what follows it
A gain the server has already committed (a rating step, a stock / production step) must not arrive as A NUMBER THAT CHANGED. Outside the surfaces that fly their own waves the one beat is `resourceTransfer/railReward.ts`: **SEED** in the transport's apply block (the rail keeps «committed − held»; the promise is checked against the DIFF of the two views — a row whose applied change is not the promised one is not held and names itself), **FLY** from a MEASURED node of what paid (the printed icon — never a synthetic point; an unmeasurable one is a named degradation and the row ticks at once), the row ticking ON THE TOUCHDOWN, and **the table's answer one beat of the animation clock AFTER the last touchdown** — a reaction (the ruling Greens' M€ on a TR step) never ticks before its cause. The owner decides when and where from; the module owns the holds and their order, so the chain survives the owner's surface leaving. Three corollaries, each paid for by TR26: ① **a DERIVED cell is held with its source** — the rail's VP total includes the rating point for point, and announced «+1» a second before the rating's token landed (`ConsoleResourcePanel.vp`); ② **a chip stays ON SCREEN for its whole flight** — a toss lifted over the higher endpoint keeps rising past it, so every flight into the rail's top rows left the viewport and came back down onto its row: `transferArcPlan(…, ceilingY)` flattens only the arcs that would cross the top edge (guard: `resourceTransferModel.spec` § the ceiling); ③ **a probe that measures the counter is not a probe of the flight** — «the rating reads N until the touchdown» was green while the token was invisible for a quarter of its flight; read the storyboard (`TM_E2E_STORYBOARD=1`) and assert the object's own box. Contract: `docs/TURMOIL_REDUX_WATER_HAULING.md` §9.3. **Its second owner is the card ACTION's commit** (`consoleActionCommitRail.ts`, TR28): a direct TR of a branch is a rail reward, and a printed row that adds to its own card and then spends from it is a TIMELINE of links — each on the previous one's touchdown, a spend leaving the capsule ticking on its DEPARTURE, the capsule never reading less than the model minus the not-yet-landed plus the not-yet-departed (`heldCardCapsule`).

## A CARD THAT ALREADY LIES ON THE TABLE TURNS WHERE IT LIES — the fourth arrival mode, `sealed-reveal`
The arrival modes are SEMANTIC (`consoleCardArrival.ts`), and the fourth one exists for a card that has been ON THE TABLE face-down before its data exists: a settlement table's later place (colony polish 1 — Pluto, k settlements). The first payout DEALS it (a cover with no face, born on the colony's printed bonus card); its cycle's batch later brings the card, and the SAME body turns over IN PLACE, once — `addCard3DTurn` on the place's own Card3DInner (a real `perspective` outer, an opacity only on the flat outer, never on the `preserve-3d` body), a beat face-down first (`sealedRevealPlan` — the eye finds the card it already knows), the deck's counter ticking −1 as the turn starts (the apply-block seed ADOPTED by the table, released at the turn). Two orders are load-bearing: the place must be STANDING (painted, opaque, still — the stage may be coming back from under the hand) and its SEAL must be gone (the discard it waited for touched down) before the turn starts; both waits are bounded. A second flight to a place that already holds a card is the defect this mode removes — the deck-draw scene and the trade's covers stand aside for that batch by construction (`settlementClaimsBatch`).
