# Card / game-logic rules

## Adding a card — the 5 required touch points
1. Card class in `src/server/cards/<module>/<CardName>.ts` — extend `Card`, or **`ActionCard`** for an ACTIVE card with a repeatable action (it enforces the `action` behavior and wires `canAct()`/`action()`).
2. Enum entry in `src/common/cards/CardName.ts`.
3. Factory registration in the module manifest (`<Module>CardManifest.ts`; base cards → `StandardCardManifests.ts`, all aggregate in `AllManifests.ts`).
4. `metadata.renderData` via the `CardRenderer.builder()` DSL.
5. Spec in `tests/cards/<module>/<CardName>.spec.ts`.

**Prefer the declarative `behavior` DSL over imperative `bespokePlay()`.** Declarative cards are auto-covered by the preview / information / reason subsystems; a bespoke card needs hooks.

## Co-location is load-bearing — never centralize per-card hooks
Every per-card hook lives **IN the card file**, next to `canPlay`/`canAct`/`bespokePlay`, pulling wording from a thin stable builder: `cardPlayPreview?()` and `actionPreview?()` (`cards/actionPreviews.ts`), `actionUnavailableReason?()` (`cards/actionReasons.ts`), `unplayableReason?()`, `metadata.infoText`, modal metadata (`inputs/optionMetadata.ts`). This is a fork that merges upstream: when upstream changes a card, the hook is in the SAME diff/conflict and can't silently drift. A fork-only central table would merge clean and rot. All hooks are READ-ONLY (never mutate game state).

## 🚫 NO AUTO-SELECT — every targetable choice is SHOWN, even with a SINGLE candidate
The player must see WHO/WHICH card is hit and its `current → resulting` BEFORE confirming. The trap is bespoke code doing `if (candidates.length === 1) { apply directly }` — build the `SelectCard`/`SelectPlayer` instead (neither auto-resolves on one option) and pre-collect it in the preview. Mirror it in BOTH `execute()` and the read-only `previewSelect*()`. `AddResourcesToCard`/`RemoveResourcesFromCard` need explicit `autoSelect/autoselect: false`.
**Exempt:** a FIXED self-target (`filter: c => c.name === this.name` — Ants/Predators) and `OrOptions.reduce()` auto-picking the only OR BRANCH (no hidden target).
Per module, grep for `length === 1` / `length > 1` near `addResourceTo` / `removeResourceFrom` / `.attack(` / `.cb(` / `production.add` — there is NO auto-guard for this class. Record triage in `docs/DELAYED_TARGET_AUDIT.md`.

## No silent loss — a skipped effect must NAME itself
When an effect can't apply (no eligible card, no target), suppress the misleading gain chip and emit a warning that names WHICH effect was skipped: `skipped: {label, effect?}` built via `actionPreviews.warningNote(...)` / `targetStepOrWarning(...)` with a label from the shared `SKIPPED_LABEL` set — never a hand-rolled `{kind:'note', noteKind:'warning'}` literal and never a bare "no valid target". Omit `effect` when no single magnitude is honest (an either/or attack).

## A HOOK THAT ANSWERS IS NOT A HOOK THAT ACTS
Where a rule must be read TWICE — once to promise (a preview) and once to pay (the commit) — the card's hook returns WHAT IS OWED and grants nothing. `ICard.deltaMovementBonus` is the reference: `delta/deltaMovement.ts` is its single caller and both the commit and the planning projection ask that same function, so a promise and a payout cannot diverge and an effect that cannot mutate cannot re-trigger the event that called it. The other half of the same contract is that the EVENT has one commit point: `commitDeltaMovement` is the only writer of a Hydronetwork position (source-level guard: `tests/delta/deltaMovement.spec.ts`), which is what makes «any player moved» true for MarsBot without a single `if (bot)`. Full write-up: `docs/claude/delta-movement-contract.md`.

## Reasons name ONE blocker
A validation reason must name one concrete blocker — never an "X or Y" combination the player has to guess between. Check conditions in order and return the specific reason. A GENUINE disjunction ("Need 1 M€ OR an asteroid" — either enables the action) keeps its "or".

## `metadata.infoText` (structured card text)
EN-only keys (the text IS the i18n key), **ONE block per bonus** (never a run-on paragraph). Three hard, guard-enforced rules:
1. **No sequencing connective words** («then» / «afterwards» / «finally» / ordinal-less «firstly») — order carries sequence.
2. **Block order = RENDER reading order = real EXECUTION order.** Behavior-derived blocks auto-sort; authored `infoText` you order yourself. If the card's render is out of execution order, fix the RENDER.
3. **The requirement LINE must state the same rule as the requirement CHIP.** Both derive from the same `CardRequirementDescriptor`, so the prose must carry the descriptor's `max` («at most», never «at least»), its magnitude, its `all` scope and its subject noun — a `max` phrased as a minimum tells the player the OPPOSITE of the chip beside it (Pioneer Settlement, Geological Survey). Every countable branch of `requirementBlock` phrases the comparator through `comparator(max)`. Guard: `tests/cards/requirementProse.spec.ts` (EN and RU).
The generator must not drop a `behavior` sub-field (placement restrictions, adjacency bonus, counts). A VP block carries ONLY the VP rule; a block about the card's own tile must tether to it via `tokens`. Metadata riding a constructor-param default needs `: CardMetadata`.

## Guard tests ARE the worklist
`npm run make:cards` regenerates `metadata.information` + `src/genfiles/cardInfoAudit.json` (`needsCuration` / `seededRunOn` / `missingTranslations` must all be 0). Coverage specs fail WITH the exact card list: `cardPlayPreviewCoverage`, `actionReasonCoverage`, `actionUnavailableReasons`, `cardInformation`, `requirementProse`, `effectExtraction`, `actionExtraction`, `choiceContext`, `premiumCardViewModel`, `premiumCardIcons` — and `promptMarkerGuard` (a file building `OrOptions` / `SelectPlayer` / `SelectColony` in premium scope must attach a structural marker — `markChoiceContext` et al. — or hold a reasoned allow-list row; see `docs/PROMPT_PREMIUM_AUDIT.md`).

**Widening scope to a new expansion → follow `docs/claude/expansion-adaptation-checklist.md` (the master to-do: which SCOPE constants to widen, per-subsystem work, per-module gotchas, done-criteria).**

## A Turmoil Redux RESOLUTION is a declaration + steps that REPORT — never a screen
Full checklist: `docs/claude/parliament-resolution-checklist.md`; guard: `tests/parliament/ResolutionContract.spec.ts` (walks `REDUX_RESOLUTION_CATALOG`, fails with the card, the step and the condition — it is the worklist). The short form:
1. **Declare, don't draw**: `scaled: InfluenceScaledEffect[]` for every influence/count/sequel-scaled part, `winnerReward` for the winner's tile — the face, the vote reading, the reward stage, the skip plate and the «Полигон» family (`familyOf(definition)`) are derived from it.
2. **A step either MUTATES or ASKS**, and in EVERY branch calls `ctx.report(outcome)` exactly once with a `kind` from `src/common/parliament/rewardAddress.ts` (two payouts = two steps; a skip names its `reason` — a translated key — and the amount it would have paid). What a step decided before a question lives in `ctx.state` (a reload re-runs `run()`).
3. **Every prompt carries a structural source** (`markChoiceContext({source:{kind:'resolution'}})` · `placementContext` via `committedPlacement` · `ExternalDrawIntake` with `cause.kind === 'resolution'`); the title is journal text only.
4. **The address table is a `Record` over the whole outcome `kind` union**: a new mechanism (`stockLoss`, `agenda`, `colonyTrack`, `tr`, `partyAccessGrant`) gets its kind + row + spec BEFORE the first card that pays it — «add the kind later» does not compile.
4b. **A card that changes THE WORLD instead of paying seats** declares `worldMoves` (data) + `worldSteps` (payout) + `text.world` (the sentence) — all three or none. A world step runs ONCE per enactment (key in `applied`, not `seatApplied`), carries NO player (the engine's `IPlayer` is a handle, never the author), and its record has no seat — so every viewer reads it. Its limits are NAMED (the card's own clause first, the arithmetic floor second — never the engine's silent early return); a lowering is a SIGNED `global-parameter-changed` event; «no one gets the TR» is `ParameterMoveOptions {unrewarded: true}` — PARITY with the World Government's phase, not a stricter mode. Reference: RX12 Gas Export, `docs/TURMOIL_REDUX_GAS_EXPORT.md`.
4d. **A LEVY** (the BUDGET family — Industrialist Budget: «lose 10 M€» FIRST) is `ResolutionDefinition.levy` (`common/parliament/resolutionLevy.ts`, one arithmetic `levyPaid` — never below zero) paid by the family's ONE shared step `levyStep(id, levy)` declared FIRST in `immediateSteps` (the printed order is the executed order); `stock.add(res, −paid, {from: {resolution}})` — without `from` the engine writes `logIllegalState`. A short seat's take is a `stock` record with the NEGATIVE amount, `owed` and its reason (never a skip); an empty supply is a named `skipped` with `owed`; both are still paid the rest — no solvency is asked. The address reads the sign (`RewardDelivery.direction: 'loss'`): the chip flies the SAME address BACKWARDS (rail → the law's negative tile), the counter ticks on DEPARTURE. Never encode a levy as a negative `InfluenceScaledEffect`. A count over PRODUCTION STEPS (`resolutionCountKind` = `production`) is the twin of a multi-tag count: `byResource` breakdown, values from `player.production`, never from cards. Reference: RX15, `docs/TURMOIL_REDUX_INDUSTRIALIST_BUDGET.md`.
4c. **A passive DISCOUNT** (Heat Capture: 3 M€ off a Building tag) is `ResolutionPassive.cardDiscount(player, card)`, asked by the ONE price function (`Player.getCardCostBreakdown` → `ParliamentHandler.cardDiscount`, a pure query — no effect scope) and itemized under `{kind: 'resolution', id, owner}` in `discounts`, never the cardless remainder — the payment head, the forecast's discount group, `discount-applied` and the journal then NAME the law. Its forecast twin IS that breakdown (`discountsOf`), so `forecast` states no fact for it. Never a player field, never a second price path. Reference: RX14, `docs/TURMOIL_REDUX_HEAT_CAPTURE.md`.
4e. **A LEVEL** (Joint Research: «draw until you have 6 + influence cards in hand») is `InfluenceScaledEffect.upTo {total}`: the formula (`scaledAmount`) yields the TARGET, the ONE `topUpAmount(effect, I, current)` yields the payout = max(0, target − level), the level read from THE ENGINE at the step (the hand). The record carries `target` + `total {before, after}` (the sequel family's member, REUSED — never a second level member) + `amount`/`drawn`; a seat at or above the target records a named `skipped` («Already at the target hand size») — the rule working, never «no influence», and the client prints it calmly («no draw needed»: no amber, no strike). Every reading prints target · level · payout together. A quest of «play N event cards» is a `cardsPlayed` goal by card TYPE (`cardType: 'event'`), never `{kind: 'tag', tag: EVENT}`: the event tag is not in `card.tags` (it follows from `CardType.EVENT`), so a tag goal sits at zero forever; the footnote draws the EVENT TAG with the count (the yellow disc with the down arrow on the scans IS the event tag, never «discard»). Reference: RX16, `docs/TURMOIL_REDUX_JOINT_RESEARCH.md`.
4f. **A count over the seat's COLONIES** (Jovian Tax Rights: «+1 M€ production per colony, max 5») is `resolutionCountKind` = `colonies` — the SIXTH kind: a colony is a CUBE of the player's on a colony tile (two on one tile are 2, another seat's cube is 0), and the number is THE ENGINE's — `ColoniesHandler.coloniesOf(game, player)` (one entry per cube, table order), the ONE reading `Counter` («colonies» countables), `Player.getColoniesCount` and the parliament's `resolutionCount` → `countColoniesToward` all stand on; never a walk of the colony table in a card. The explanation is the LIST of tile names (`ResolutionCountModel.colonies`, record/model `countedColonies`, reading `countedColonies`, «Luna ×2 · Titan»), never a second model — and NOT Colonial Affairs' `colonyBonuses` registry, which is per TILE and about bonuses. A counted part at `perInfluence: 0` has NO influence term (`yieldInfluenceEnters`): its formula prints no «+ 0 / [influence]» and its reading no «+ [influence] N», while its cap (`cap` on THAT part alone) prints with it; a production part beside a SUPPLY part of the same card wears the HORIZON with or without a levy (`productionHorizonOn`). Zero colonies is a NAMED skip («No colonies»), distinct from the titanium's «No influence» — the card pays one part and skips the other. `compatibility` is never declared (colonies are mandatory in Redux). Reference: RX17, `docs/TURMOIL_REDUX_JOVIAN_TAX_RIGHTS.md`.
4g. **A card-resource unit of SEVERAL KINDS** (Medical Database: «add 1 data or microbe resource to any card…») is `unit: {kind: 'cardResource', resources: [DATA, MICROBE], spread: true}` — `resources` is a LIST everywhere, one kind being the list of one (Aquifer, Cloud Development); a second declaration shape does not exist. «Data or microbe» is NEVER a second question to the player: a card has ONE storage rule, so the shared step (`AddResourcesToCards(player, [DATA, MICROBE], N)` — `AddResourcesToCard` takes the same list) UNITES the holders of every kind (tableau order, each once, `WARE` a holder of any) and the kind of every unit is the kind of the card it lands on (`ResourcePlacement.resource` = `holderResourceOf(card)`; a WARE holder journals its own resource — its state is a counter, not a kind). The marker names the kinds (`cardResources`) and each candidate's own (`cardResourceByCard`) instead of one `cardResource`; the record carries `resources` (the declared kinds) and `cards[].resource` (each card's), and `resource` ONLY when every landed unit is of one kind; the client draws the unit as ONE icon set joined by «or» (`ConsoleYieldUnit`), flies each chip in its card's kind, and reads the honest «no recipient» note over the holders of ANY kind (`holdsAnyOf`). No holder of either kind is a NAMED skip with its size («No card can hold data or microbes»), apart from «No science tags and no influence». A stand scenario of the distributed family declares `holds` (the kinds its holders take) — listed only under a law whose unit spans them. Reference: RX18, `docs/TURMOIL_REDUX_MEDICAL_DATABASE.md`.
4h. **A passive that changes the VALUE OF A RESOURCE** (Metal Research: «each unit of steel and titanium is worth 1 M€ extra») is `ResolutionPassive.resourceValueBonus(player, resource)`, asked by the ONE value accessor (`Player.getSteelValue` / `getTitaniumValue` = the player's own field + `ParliamentHandler.resourceValueBonus`, a pure query gated on `participates`, no effect scope) ON THE READ — the serialized `steelValue` / `titaniumValue` FIELD is never written by a law (`increase*` at the enactment / `decrease*` at the change is forbidden: a save from under the law would need «did I already add mine», the floor of `decrease*` removes whoever's unit, and the drift is invisible). Stacks additively with Advanced Alloys and its kin, survives a save by construction (the spec: field 2 / 3 while the accessor reads 3 / 4), ends the instant another card takes the ENACTED slot, applies BEFORE the Luna Trade Federation −1. Every reader of the value goes through the accessors — a raw read of the field (`spendableMegacredits` once) silently loses the law; `serialize` / `deserialize` read the field on purpose. Its forecast twin is the RATE where the decision is made (the rail's value badge, the payment panel's «×N» — both read the model's live value), so `forecast` states nothing; a value is NOT a discount (`getCardCostBreakdown` untouched, `discounts: []`). Two payouts = two steps and two records, the family's own rows word for word. Reference: RX19, `docs/TURMOIL_REDUX_METAL_RESEARCH.md`.
4i. **A count over the BOARD is of ONE OF TWO MEASURES, and the declaration says which** (Migration Funding: «2 M€ per city on Mars — each city in a stack counts separately»): `resolutionCountKind` = `{kind: 'board', tiles, measure: 'cells' | 'tiers'}`. `cells` — a cell is ONE unit whatever stands on it (the space cities; Skyscrapers' `marsCities`, the DESTINATIONS of a tier: a stack is one place to land); `tiers` — the stacks are SUMMED and the number is THE ENGINE's quantity (`MarsBoard.countCities(player, 'onmars')`, the one function Mayor, Metropolist and the countables sum by), NEVER the cell list's `.length`. The two counts over one tile read the SAME cells, agree on every board without a stack and part by exactly the stack — so a quantity gets its OWN id (`marsCityTiers`), never `marsCities` reused, and the spec pins the divergence (3 vs 4 on one table). The explanation keeps the CELLS with their HEIGHTS: `ResolutionCountModel.tiers` (a column aligned with `spaces`, the twin of `units` for cards), record/model `countedTiers`, reading `countedTiers` — a cell is listed ONCE, never duplicated per tier. The stack arithmetic is ONE module in `common/boards/cityStack.ts` (the server's `boards/cityStack.ts` is its typed door), read by the engine's quantity and by the stand's `countSpacesToward` alike (`CountedSpaceFacts.stackHeight`). A zero is «No cities on Mars and no influence», never «no influence»; the tile glyph is BARE (the spark is the space city's — `countedTileSpark`). Reference: RX21, `docs/TURMOIL_REDUX_MIGRATION_FUNDING.md`.
4j. **The winner's part can be a STEP OF A PARAMETER — rewarded, unlike a world move** (Mohole Contest: «the player that won this resolution increases the global temperature 2 steps»): `winnerReward: {kind: 'parameter', parameter: 'temperature' | 'oxygen' | 'venus', steps}` (`common/parliament/winnerReward.ts` — the THIRD kind beside a tile and a colony; an ocean is a TILE, never a step) paid by the family's ONE shared executor `winnerParameterStep(id, reward)` (`resolutions/WinnerParameterStep.ts`) listed in `winnerSteps` under `winnerParameterStepKey(reward)` = the parameter's id — the guard refuses the declaration without its step and the step without its declaration. The executor NEVER passes `unrewarded`: the political phase is `PARLIAMENT`, so the engine's own gate pays the WINNER everything a raising player gets — +1 TR per step actually made, the track's bonuses (the −24/−20 °C heat production, answered by the ruling Greens), its card hooks, and the 0 °C ocean as a placement of the winner's OWN. `unrewarded: true` is the WORLD move's flag (Gas Export, Heat Capture) — passing it here silently takes the winner's TR away (the guard: a winner record flagged `unrewarded` fails). The ROOM is the shared `parameterRoom` (now carrying `heatProductionBonus` / `oceanBonus` for a temperature RAISE); the ceiling is NAMED (one step from it → one step; at it → a `skipped` with the parameter's own reason), never the engine's silent return; the record is `kind: 'globalParameter'` + `part: 'winner'` with the steps made, before/after and **`tr` MEASURED around the call**. THE ENGINE'S TAIL OF A MUTATING STEP IS DRAINED BEFORE THE NEXT STEP (`ParliamentPhase.stepEffects` → `drainDeferred` after every seat / world / winner step): the ocean is placed while the seats after the winner wait, and the model publishes it as the step's own ask (`pending` from the reaction window `scan` when no step is asking) — the client reads a `space` prompt with no resolution source + `pending` on the viewer as a TAIL placement (`sittingTailPlacementOf`): the reward page is held, the crumb names «РАЗМЕЩЕНИЕ», it stands behind the SAME door as the winner's tile (`parliamentPlacementDoorClosed` — admitted at once it took the screen before the step's wave had flown) but the sitting's WALK opens the door once its page is quiet (never a press), and the planet beat (`parliamentWorldBeat` — every `globalParameter` record, world or winner) does not resume the stack while the board still has the seat's business. Reference: RX23, `docs/TURMOIL_REDUX_MOHOLE_CONTEST.md`.
5. **Forbidden**: any resolution id / import of `server/parliament/resolutions` under `src/client/**` outside the manifest and the stand (guard 6); a per-card screen, class or choreography; a party reaction written inside a card (the driver records `kind:'reaction'` from the recorder's events); recomputing a payout on the client.
